# 오대덕 사업 검증 하네스

`INTENT.md`의 범용 탐색·분석 목표 안에서 사업 가설의 유용성과 상업적 검증을 구분한다. 한 구매자에
대한 실험은 검증 단위이며, 범용 제품 전체를 그 구매자나 데이터셋에 맞춰 축소하는 근거가 아니다.

## 요청 단계에 맞춘다

- **아이데이션·브레인스토밍**: 사용자 문제, 실제 데이터가 지지하는 전제, 의미적으로 먼 자료의 연결,
  기존 대안, 가정과 가장 싼 반증 방법을 가진 가설을 만든다. 이 산출물에 결제 증거를 완료 조건으로
  추가하지 않는다. 복수 후보 요청은 비교 가능한 후보로 답하고, 검증된 수익성이라고 부르지 않는다.
- **사업 선택·수익화 검증**: 아래 전체 흐름으로 `구매자 → 현재 업무 → 손실/위험 → 데이터 edge →
  행동 → 지불`의 증거 사슬을 평가한다. 결제 없는 `GO`는 허용하지 않는다.

단계는 사용자 요청에서 정한다. 결제 근거가 없다는 이유로 사업 검증 요청을 아이데이션으로 낮추지
않으며, 단순 가설 생성에 인터뷰·영업을 요구하지도 않는다. 실제 고객 접촉·판매·결제는 별도 권한이
필요하다. 제품 아키텍처 검토에서는 관련 판단 기준만 적용하고 시장 조사 전체를 재시작하지 않는다.

## 렌즈

외부 스킬 설치 없이 요청 단계에 관련된 렌즈를 적용한다. 고객의 말과 결제가 없으면 가정으로 표시한다.

1. **고객 증거**: 고객이 자발적으로 쓴 말에서 고통, 촉발 사건, 원하는 결과, 현재 대안을 추출한다.
   인터뷰에서는 의견보다 최근 실제 사례를 열어 사용한 화면, 파일, 결재자, 지출을 확인한다.
2. **아이디어 압박**: 문제가 즉시 해결할 만큼 아픈지, 지금 가능해진 외부 변화가 있는지, 코드를 쓰기
   전에 수작업 결과물을 팔 수 있는지 검사한다.
3. **경쟁 구조**: 기술 카테고리가 아니라 제품이 사라졌을 때 고객이 고용할 대안을 경쟁자로 본다.
   기존사가 따라 할 수 없는 이유와 따라 하지 않을 이유를 분리한다.
4. **첫 결제**: 한 역할·한 상황·한 결과로 좁히고, 창업자 주도의 수작업 서비스와 디자인 파트너를 통해
   결제와 반복 사용을 확인한다.

### 넓은 후보가 필요할 때

발산과 평가는 분리한다. 규제자, 경쟁자, 구매자, 현장 운영자 등 문제에 맞는 관점을 고른다. 후보 수와
관점 수는 요청 범위에 맞춘다. 독립 발산이 필요한 경우에만 격리된 하위 작업자를 사용하고, 순차 발산은
독립 평가라고 주장하지 않는다.

후보가 나온 뒤 문제 적합성, 근거의 강도, 대안 대비 차이, 실행 비용으로 비교한다. 근거 없는 고정
가중치로 정밀한 순위를 만들지 않는다. 숨은 비용과 전제 때문에 매력적으로 보이는 함정을 함께 표시한다.

## 1. 결정 단위를 고정한다

한 문장으로 다음을 쓴다.

> `[구매자]`가 `[촉발 사건]`에 `[현재 대안]` 대신 돈을 내고 `[행동/결정]`을 끝내게 할 수 있는가?

`모든 기업`, `데이터 사용자`, `더 빠른 검색`이 남아 있으면 구매자 또는 행동을 더 좁힌다. 완료 조건은
예산 책임자, 실사용자, 구매를 촉발하는 사건, 바뀌는 행동이 각각 이름 붙은 상태다.

## 2. 기존 증거를 먼저 읽는다

관련된 파일만 선택해 읽는다.

- 경쟁과 수요: `docs/research/competitive-workflow-audit.md`,
  `docs/research/competitor-and-demand-cross-validation-2026.md`
- 최근 사업 후보: `docs/research/deep-monetizable-cross-domain-opportunity-2026-09.md`
- 연결 능력과 한계: `docs/specs/cross-domain-connection-discovery-v1.md`,
  `docs/research/connection-discovery-evaluation.md`
- 실제 provider 계약: `docs/provider-adapters.md`

기존 결론은 출발점이지 사실이 아니다. 조사일 이후 바뀔 수 있는 가격, 제품 기능, 법·정책, 데이터
계약은 공식 최신 원천으로 다시 확인한다.

## 3. 대안부터 조사한다

최소한 다음 네 대안을 각각 확인한다.

- 아무것도 하지 않기
- 사람, 엑셀, 검색, 대행사 같은 수작업
- 정부의 무료 포털·업무 시스템
- 직접 경쟁사와 인접 제품

공급사 공식 제품·가격·고객 페이지와 정부 원문을 우선한다. 검색결과 문구, 집계형 시장보고서,
출처 없는 TAM은 결론의 근거로 세지 않는다. 경쟁사 수보다 고객이 이미 맡긴 업무 범위를 기록한다.

완료 조건은 직접 대체재 두 개 이상과 무료/수작업 대안이 있고, 각 대안에서 고객이 바꾸기 싫어할
구조적 이유가 적힌 상태다.

## 4. 데이터 edge를 실증한다

공공데이터 발견·접근 검증은 오데덕의 실제 카탈로그 검색과 가능하면 `inspect_dataset`으로 수행하고
다음을 기록한다. 일반 웹 검색은 시장·경쟁·공식 방법론 확인에 쓰며 오데덕 실증을 대신하지 않는다.

| 계약 | 확인할 것 |
| --- | --- |
| 범위 | 포함 기관·기간·행 수와 빠진 모집단 |
| 시간 | 사건일, 공개일, 갱신주기, 지연 |
| 식별 | 사업자·법인·인허가·바코드·모델·주소 등 join key |
| 접근 | REST/FILE/LINK, 승인 방식, provider 계정, 호출 한도 |
| 행동 | 이 edge가 어떤 고객 결정을 실제로 바꾸는지 |

기관명·상품명 fuzzy match만 남으면 자동 확정하지 않는다. 동일 대상, 지역·기간 비교, 사건 관계는
각각의 식별·범위 계약으로 검증하며 단순 동시 발생을 동일성이나 인과로 바꾸지 않는다.
`미발견`은 `사건 없음`으로 표현하지 않는다. 연결을 실행했다고 가설의 유용성이나 지불의사가 입증되지는 않는다.

완료 조건은 `고객 입력 → 공식 원장 → 사건 → 행동`의 모든 edge에 식별자와 provenance가 있거나,
끊긴 edge가 제품의 핵심 위험으로 명시된 상태다.

## 5. 돈의 증거를 등급화한다

강한 것부터 기록한다.

1. 결제, 발주서, 갱신, 유료 디자인 파트너
2. 실제 화면을 연 workflow walkthrough와 고객 데이터 제공
3. 경쟁사의 공개 가격·실제 고객, 예산이 붙은 정부 조달·지원
4. 인터뷰의 호의적 의견, 온라인 반응, 시장규모 추정

1등급이 없으면 `GO`라고 쓰지 않는다. `검증 진행`으로 두고, 무엇이 관찰되면 등급이 올라가는지 적는다.
숫자는 출처 또는 계산식을 붙이며, 모르는 CAC·LTV·시장점유율은 빈칸으로 남긴다.

## 6. 가장 싼 반증 실험을 설계한다

사업 검증에서는 코드를 더 만들기 전에 수작업 또는 컨시어지 결과물로 반증할 실험을 설계한다.
실제 실행은 사용자 권한 범위에서만 한다. 실험에는 다음이 들어간다.

- 실제 구매자 수와 접촉 경로
- 고객이 제공해야 할 실제 원장 또는 입력
- 현재 대안과 비교할 과거 사건 재생
- 정밀도, coverage, 행동 변화, 결제의 통과선
- 날짜가 있는 중단 조건

“관심 있다”는 통과가 아니다. 독립 고객의 입금이나 취소 불가 발주서가 기본 결제 증거다.

## 강제 탈락 패턴

- 데이터셋 수와 멋진 연결 그림을 고객 가치로 대신한다.
- 정부 시스템을 원천으로만 보고 같은 업무를 무료로 해결하는 경쟁자로 세지 않는다.
- 경쟁사의 공개 가격을 우리 제품의 지불의사로 전용한다.
- 이름 fuzzy match를 자동 행동에 연결한다.
- 검색 시간이 줄었다는 사실을 바뀐 고객 결정이나 줄어든 손실 없이 가치로 주장한다.
- 1순위가 실패하자 구매자와 문제를 넓혀 같은 가설을 살려낸다.

## 결과 형식

아이데이션 요청에는 근거·가정·대안·반증 방법이 있는 후보를 요청한 범위로 제공한다. 상업 검증 단계와
남은 근거를 명시한다. 기존 기록을 갱신할 수 있으면 동일한 내용의 새 연구 문서를 만들지 않는다.

사업 선택·수익화 검증에서는 한 개의 versioned Markdown 결정 기록을 `docs/research/`에 남긴다.

1. 한 문장 결정과 확신 수준
2. 구매자·촉발 사건·현재 대안·바뀌는 행동
3. before/after 업무 흐름
4. 데이터 graph와 edge별 계약·누락
5. 직접·무료·수작업 대체재
6. 지불 증거와 아직 모르는 사업 수치
7. 14~30일 반증 실험과 중단 조건
8. 근거 링크, 조사일, 조사 한계

이 단계의 마지막에는 하나만 선택한다: `GO`, `검증 진행`, `보류`, `폐기`. 단일 사업 선택 요청을 후보
나열로 대신하지 않는다. 구현 요청이 따로 없다면 조사 결과만 남기고 제품 코드는 바꾸지 않는다.

설계에 참고한 외부 자료와 채택·제외 이유는 `docs/agents/harness-sources.md`에 기록한다. 실행에는 해당
저장소나 외부 스킬 설치가 필요하지 않다.
