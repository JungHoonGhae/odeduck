# apply 리팩터링 라이브 검증

Type: task
Status: open

## Question

`feat/apply-probe` 브랜치에 **라이브 검증이 끝나지 않은 `apply` 리팩터링**이 서 있다.
클린룸 실행은 전적으로 `apply` 에 달려 있으므로, 이것이 동작한다는 증거 없이는 지도의
나머지가 모래 위에 있다.

이 브랜치를 머지해도 되는가?

## 배경

`apply` 의 네비게이션과 폼 채우기를 `onApplyForm` 으로 추출해 프로브(`ProbeApplyForm`)와
같은 경로·같은 셀렉터를 쓰게 만들었다. 프로브가 다른 경로를 타면 아무것도 증명하지 못하기
때문이다. 리팩터링 중 실제 결함도 하나 나왔다: 기존 `apply` 는 폼 구조 검증을 `#reqForm`
존재 여부 하나로만 했고, 목적분류 라디오나 이용동의 체크박스가 사라져도 `fn_save()` 를
실계정에 호출했다. 지금은 5개 요소를 모두 확인하고 하나라도 없으면 제출을 거부한다.

단위 테스트는 통과하지만, **브라우저를 띄워 실제 포털을 상대로는 한 번도 돌지 않았다.**

## 해야 할 일 (HITL — 사람의 로그인 필요)

1. `gongctl login` (브라우저 1회)
2. `gongctl doctor` — `apply` 점검이 `ok` 인지 확인. 카나리 pk 가 이미 신청된 것이면
   `--apply-pk` 로 신청하지 않은 pk 를 지정한다.
3. **실제 활용신청 1건** 을 리팩터링된 코드로 수행해 성공을 확인한다. 되돌릴 수 없으므로
   사용자 동의가 전제다. 이것 없이는 리팩터링이 안전했다는 증거가 없다.
4. 통과하면 머지 후 릴리즈, 실패하면 원인 기록 후 티켓 재개.

## 좋은 답의 모양

doctor 의 apply 행 출력 + 실제 신청 결과(성공/실패와 메시지) + 머지 여부 결정.
실패했다면 어느 셀렉터·어느 단계에서 깨졌는지.
