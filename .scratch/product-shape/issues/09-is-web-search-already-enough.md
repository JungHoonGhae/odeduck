# 웹 검색이 이미 충분한가

Type: prototype
Status: open

## Question

이 제품의 진짜 대안은 경쟁 도구가 아니라 **"LLM 이 웹에서 알아서 찾아준다"** 이다.
소유자 본인이 그래서 시도조차 하지 않는다고 말했다.

**웹 검색이 증명 가능하게 실패하는 질문의 계급이 존재하는가? 얼마나 큰가?**

## 검증 방법

실제 질문 **8~12개**를 준비해 두 경로로 답하고 나란히 비교한다.

- 경로 A: 웹 검색만 (지금 하듯이)
- 경로 B: gongctl 로 데이터셋을 찾아 신청·호출해서 계산

질문은 **미리** 만들어 고정한다. 결과를 보고 유리한 질문만 남기면 실험이 아니다.
구성은 의도적으로 섞는다:

- 웹에 답이 있을 법한 것 (대조군 — 여기서 B 가 이기면 실험 설계가 틀린 것이다)
- 최신성이 필요한 것 (오늘/이번 주 수치)
- 집계·교차가 필요한 것 (여러 기관 데이터를 붙여야 나오는 수)
- 아무도 기사로 쓴 적 없을 법한 것 (롱테일 행정 데이터)

## 각 질문에 대해 기록할 것

- A 가 답을 냈는가? 냈다면 **출처가 1차 데이터인가 기사 재인용인가**, 시점은 언제인가
- A 의 답이 **틀렸거나 오래됐는가** (B 로 확인)
- B 가 답을 냈는가, 얼마나 걸렸는가
- 사람이 봤을 때 **어느 답을 신뢰하겠는가**

## 판정 기준 (미리 고정)

- **계급이 있다**: 질문의 1/3 이상에서 A 가 못 내거나, 냈지만 틀렸거나 오래됐다.
  그리고 그 실패에 **패턴**이 있다(최신성 / 교차 / 롱테일 중 무엇인지 말할 수 있다).
- **계급이 좁다**: 실패가 있지만 패턴이 없고 흩어져 있다 → 도구는 특정 상황용 유틸리티다.
  일반화에 큰 투자를 할 근거가 없다.
- **계급이 없다**: A 가 거의 다 이긴다 → 접근 자동화는 풀 가치가 있는 문제가 아니다.
  이 경우 지도는 다른 목적지로 다시 그려져야 한다(예: 카탈로그·명세 surface 가 진짜 가치).

## 왜 이게 첫 번째인가

싸고(며칠이 아니라 몇 시간), 이 지도에서 가장 비싼 티켓을 죽일 수 있다.
그리고 여기서 나온 실패 패턴이 seed set 을 고르는 근거가 된다 — 어떤 종류의 데이터가
웹으로 안 나오는지 알아야 어떤 문을 열지 정할 수 있다.

## 주의

**결과가 "웹이 이긴다"로 나올 가능성을 진지하게 받아들일 것.** 그 답도 유효한 산출이고,
그 경우 이 지도는 목적지를 다시 그린다. 유리한 결과가 나올 때까지 질문을 바꾸지 않는다.
