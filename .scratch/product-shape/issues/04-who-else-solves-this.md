# 이 문제를 이미 누가 풀고 있나

Type: research
Status: resolved

## Question

"에이전트가 외부 서비스의 접근 권한을 스스로 획득한다"는 문제는 이미 시장이 있다.
**우리가 서 있는 자리가 빈 자리인지, 이미 붐비는 자리인지** 확인하지 않으면 일반화 실험이
성공해도 의미가 없을 수 있다.

## 먼저 짚을 것

진짜 베이스라인은 이 도구들이 아니라 **웹 검색을 하는 LLM** 이다(`09` 참조). 이 티켓은
그 다음 층위 — 접근 자동화라는 문제 자체에 이미 사람이 있는가 — 를 본다.

## 확인할 것

- **Composio / Arcade.dev / Nango / Anon / Paragon** — 에이전트용 서드파티 인증·연결 계층.
  이들이 다루는 것은 대부분 **OAuth 가 이미 있는 SaaS** 다. 우리 문제(가입·심사·승인 대기가
  있는 포털)를 다루는가? 다루지 않는다면 그 경계가 우리의 자리다.
- **browser-use / Skyvern / Stagehand** — 브라우저를 LLM 이 직접 모는 범용 도구. 이들이
  "임의 포털에서 접근 획득"을 이미 충분히 해내는가? 해낸다면 gongctl 의 일반화는
  thin wrapper 가 된다(steipete 의 반증 기준).
- 한국 소스에 특화된 시도가 있는가.

## 왜 이게 중요한가

이 지도의 가설은 "접근 획득이 병목"이다. 그 병목을 이미 잘 푸는 도구가 있다면 가설은
살아도 우리의 자리는 없다. 반대로 **범용 브라우저 에이전트가 승인 대기·키 발급·전파 지연
같은 것을 못 다룬다면**, 그 부분이 정확히 우리가 이미 손으로 검증한 영역이다.

## 좋은 답의 모양

각 도구가 실제로 다루는 범위(1차 출처 기준)와, 우리 문제와 겹치지 않는 지점 한 문장.
그리고 "이미 있다"면 그 사실을 정면으로 인정한 뒤 지도에 미치는 영향.

## Answer

세 층으로 나뉘고, **우리와 겹치는 것은 한 층뿐이다.**

### 1층: 에이전트용 인증 플랫폼 — 겹치지 않는다

**Composio, Arcade.dev, Nango, Paragon** 은 "에이전트가 서드파티 도구를 쓰게" 해준다.
확인 결과(Composio 공식 문서 직접 확인):

> 사용자가 **이미 가진 계정**을 연결한다 — Gmail·GitHub·Slack 을 OAuth 로 잇고, 토큰을
> 저장·갱신한다. **계정 생성·개발자 앱 등록·API 접근 승인 신청을 자동화한다는 언급은 없다.**

즉 이들이 푸는 것은 **"내 계정이 있는 SaaS 에 토큰으로 붙기"** 이고, 우리 문제인
**"계정도 없고 승인 절차가 있는 포털에서 접근 권한을 얻기"** 는 다루지 않는다. 이 경계는
분명하며, 우리 자리를 침범하지 않는다.

(참고: Composio 는 2026-05 에 고객 API 키·GitHub OAuth 토큰 대량 유출 사고를 공개했다.
자격증명을 중앙에 모으는 모델의 위험을 보여주는 사례 — 우리는 키를 로컬에 두므로 이 위험
구조를 공유하지 않는다. 이건 반증이 아니라 설계 대비점이다.)

### 2층: 범용 브라우저 에이전트 — **정면으로 겹친다**

**Skyvern** 은 우리가 손으로 만든 것과 같은 일을 범용으로 주장한다(GitHub README 직접 확인):

- "**처음 보는 웹사이트에서도 동작한다** — 시각 요소를 액션에 매핑하므로"
- "**폼 입력을 채우는 것이 기본 기능**"
- 로그인 자동화, **2FA(TOTP)**, 비밀번호 관리자 연동, 클라우드판은 CAPTCHA 우회까지
- 제품 페이지: "신청서·등록서·규정 서류를 **어떤 사이트에서든 대규모로 제출**"

**우리가 `apply` 에서 한 일 — 낯선 포털의 폼을 몰아서 제출하는 것 — 은 커모디티다.**
이걸 인정하지 않으면 지도가 거짓 위에 선다.

다만 Skyvern 이 **하지 않는다고 문서가 밝히는 것**도 분명하다:

- **키 발급 이후를 다루지 않는다** — 로그인 후 자격증명을 꺼내 관리한다는 주장이 없다.
- **무엇이 존재하는지 모른다** — 어떤 서비스·데이터를 신청할지 탐색하는 기능이 없다.
- 방식이 다르다: **비전 LLM 이 매 단계 판단**(WebBench 정확도 64.4%). 우리는 결정적
  스크래퍼다. 11,932건 카탈로그를 훑거나 매 호출마다 도는 용도로는 비용·정확도가 맞지 않는다.

### 3층: 한국 소스 특화 — 비어 있다

이전 조사에서 확인된 그대로: `Koomook/data-go-mcp-servers`(⭐288, 2025-09 이후 방치, API 6개
하드코딩·키 수동), `JeHwanYoo/data-go-kr`(⭐1, 방치). **활용신청을 자동화한 것은 여전히 없다.**

## 이 지도에 미치는 영향

1. **"폼을 몬다"는 차별점이 아니다.** 일반화 프로토타입(`02`)의 성공 기준에서 이 항목의
   가중치를 낮춰야 한다. 우리 뼈대 5단계 중 3번(페이지 자기 제출함수 구동)은 Skyvern 이
   더 일반적으로 해낸다.
2. **차별점이 있다면 그 위층이다** — 무엇이 존재하는지(카탈로그), 명세를 어떻게 읽는지,
   키를 어떻게 꺼내 호출에 주입하는지, 승인·전파를 어떻게 기다리는지. A 팔 실패 분석이
   가리킨 "동적 페이지 벽"도 **브라우저로 매번 긁는 것이 아니라 키를 받아 API 로 부는 것**이
   답이었다. 그 구분이 이 제품의 자리다.
3. **따라서 `02` 의 질문을 다시 써야 할 수 있다**: "뼈대가 일반화되나"가 아니라
   **"폼 구동을 남의 것(Skyvern 등)에 맡기고 우리는 그 위층만 소유할 수 있나"**.
   그렇다면 유지보수 표면이 크게 줄어 부트스트랩 제약과도 맞는다.
   → 이건 `02` 를 열 때 반영한다.
