# 자연어 의미 검색 평가: 키워드 검색보다 실제로 무엇을 더 찾는가

평가일: 2026-08-31 (Asia/Seoul)
평가 대상: `gongctl` 작업 트리(`HEAD 2c2b5c5301f4`)의 로컬 카탈로그 검색
결론: **의미 벡터는 유의미하지만, 벡터만으로는 충분하지 않다. 가장 좋은 형태는 `사용자 목표 → 모델이 데이터 축을 계획 → 축별 lexical + semantic 하이브리드 검색`이다.**

## 요약

11,902개 공공데이터 카탈로그 중 실제 명세가 있는 REST 7,130개를 대상으로, 키워드를 일부러 정답처럼 쓰지 않은 한국어 사용자 목표 10개를 평가했다. 주 비교 조건마다 top 10씩 100개, 총 300개 결과를 공식 카탈로그 제목과 설명으로 수동 판정했고 절제 실험 100개를 별도로 판정했다.

| 검색 조건 | Precision@10 | 관련 기회축@10 | 일반 검색 top 10에 없던 관련 결과 |
|---|---:|---:|---:|
| 자연어 lexical (`--semantic=false`, concepts 없음) | 0.36 | 1.2 | 기준선 |
| 자연어 hybrid semantic (concepts 없음) | 0.66 | 2.3 | 46개 쿼리-결과 쌍 |
| 모델 계획 + hybrid semantic (concepts 있음) | **0.78** | **3.7** | **68개 쿼리-결과 쌍** |
| 참고 절제 실험: 모델 계획 + lexical | 0.66 | 3.2 | 52개 쿼리-결과 쌍 |

핵심 해석은 세 가지다.

1. **벡터 검색 자체가 의미가 있다.** 사용자의 문장을 그대로 넣었을 때 P@10이 0.36에서 0.66으로 올랐다. 예를 들어 “동네에 새 가게를 열었을 때 잘될 자리”라는 문장은 lexical top 10에서 관련 결과가 하나도 없었지만, 의미 검색은 `상권 점포이력`, `상권 변화지표`, `상권 집객시설`을 1~3위에 놓았다.
2. **가장 큰 제품 가치는 단순 동의어가 아니라 기회에 필요한 데이터 축을 만드는 데 있다.** 농산물 가격 예측은 가격 데이터만으로 끝나지 않는다. 계획형 검색은 lexical이 놓친 `벼 작황`, `농업기상 상세 관측`, `수입축산물 월별 수입량`을 찾아 실제 예측 서비스의 입력 변수를 넓혔다.
3. **벡터만 믿으면 안 된다.** “우리 회사가 받을 수 있는 돈과 사업 기회”에서는 concepts 없는 의미 검색이 lexical보다 낫지 않았고 둘 다 P@10 0.20이었다. 반대로 정확한 검색축을 만든 뒤 하이브리드로 검색하면 지원사업·창업·입찰 공고를 찾았지만, 이 쿼리에서는 concepts+lexical(0.80)이 concepts+hybrid(0.50)보다 오히려 좋았다. 정확한 lexical 일치가 의미상 비슷하지만 실행 불가능한 데이터에 밀리지 않도록 순위 안전장치가 더 필요하다.

따라서 현재 단계에서 별도 벡터 DB는 필요하지 않다. 11,902건 × 768차원 플랫 인덱스는 로컬 파일 약 51MB이고, 고사양 테스트 장비에서 의미 검색 10회가 3.00초였다. 검색 품질 병목은 ANN이 아니라 **질의 계획, 관련성 판정, 설명 밖의 endpoint 메타데이터 부족**이다.

## 연구 질문과 비교 조건

질문은 다음과 같다.

> 사용자가 공공데이터의 정식 명칭이나 기관 용어를 모른 채 돈을 벌 기회, 새로운 서비스, 현재 상황을 자연어로 설명했을 때 의미 검색이 일반 검색보다 관련 데이터와 예상하지 못한 인접 신호를 더 잘 찾는가?

모든 검색은 `--limit 10 --rest-only --format json`으로 고정했다.

- **L — 자연어 lexical:** 원문만 검색, `--semantic=false`.
- **V — 자연어 hybrid semantic:** 원문만 lexical+벡터로 검색, `--semantic=true`.
- **HV — 계획형 hybrid semantic:** 원문과 4개의 모델 추론 검색축을 lexical+벡터로 검색.
- **PL — 계획형 lexical 절제 실험:** 같은 검색축을 사용하되 `--semantic=false`. HV의 개선이 검색축 때문인지 벡터 때문인지 구분하기 위해 추가했다.

V와 HV는 순수 semantic-only가 아니라 현재 구현의 lexical/semantic 결합 결과다. PL은 요구된 세 조건 밖의 보조 절제 실험이다.

## 판정 기준

관련성은 API 제목만 보지 않고 로컬 카탈로그에 저장된 data.go.kr 공식 설명까지 읽어 이 문서 작성자가 이진 판정했다. 다음 조건을 모두 적용했다.

- 사용자의 목표에 직접 쓰이는 관측값, 목록, 가격, 상태, 선행지표 또는 실행 가능한 공고여야 한다.
- 단어 하나만 우연히 맞거나, 일반 지식·홍보·사례·첨부파일만 제공하는 결과는 제외했다.
- 지역 한정 API라도 목표에 맞는 측정값이면 관련으로 보았다.
- `관련 기회축@10`은 관련 결과들을 서로 다른 사업/인과 입력으로 수동 분류한 개수다. 같은 기관의 유사 API 여러 개는 한 축으로 묶었다.
- `숨은 관련 결과`는 V 또는 HV의 관련 결과 중 **같은 자연어 L top 10에 없는 PK**다. lexical로 영원히 찾을 수 없다는 뜻은 아니며, 사용자가 정확한 키워드를 다시 발명하면 더 아래나 다른 검색에서 찾을 수 있다.

PL 절제 실험은 P@10 0.66, 관련 축 3.2, 숨은 관련 결과 52개였다. 따라서 다음처럼 해석하는 것이 맞다.

- V가 L보다 30%p 높은 것은 모델 검색축 없이도 **벡터가 자연어-카탈로그 용어 간 간극을 실제로 줄인 효과**다.
- PL이 L보다 높은 것은 **질의를 여러 인과 축으로 분해한 효과**다.
- HV가 PL보다 12%p 높고 축도 3.2에서 3.7로 늘어난 것은 **계획과 벡터가 대체재가 아니라 보완재**라는 증거다.
- 단, Q4처럼 벡터 결합이 정밀 lexical 결과를 밀어내는 개별 실패가 있으므로 평균 개선만으로 semantic 가중치를 고정하면 안 된다.

일반 lexical 검색은 여러 단어가 모두 들어간 결과가 없을 때 일부 단어 OR 일치로 완화된다. 이 10개 자연어 질의에서 완화 후보 수 중앙값은 1,457건이었다. “회사”, “사업”, “지역”, “물건” 같은 넓은 단어가 인기도 높은 무관 데이터와 결합해 첫 페이지를 채우는 것이 주된 실패 형태였다.

## 일반 검색으로 묻혔던 실제 기회

다음은 제목이 그럴듯한 예시가 아니라 공식 설명 내용까지 확인한 결과다.

### 창업 입지: 자연어만으로 상권 전문 용어를 복원

Q2의 lexical top 10은 수질, 교육일정, 체육시설, 날씨 등 관련 0건이었다. V는 다음을 1~2위로 찾았다.

- `15095253 부산광역시_상권 점포이력정보서비스`: 주소·업종·좌표뿐 아니라 개업일과 폐업일을 제공해 점포 생존·폐업 추이를 만들 수 있다.
- `15095252 부산광역시_상권 변화지표정보서비스`: 상권 성장·쇠퇴·잠재력, 평균 생존/폐업 개월수를 제공한다.

HV는 여기에 업종별 평균매출, 유동인구, 상가 위치를 서로 다른 축으로 섞었다. “상권 변화지표”라는 정확한 용어를 모르는 사용자가 발견할 가능성이 크게 높아졌다.

### 가격 예측: 정답 데이터 하나가 아니라 예측 피처 묶음을 발견

Q7에서 L과 V는 가격 API만으로도 P@10이 높았지만, 대부분 같은 가격 계열이라 축 다양성은 각각 2와 1이었다. HV는 다음을 함께 찾았다.

- `15156069`: 조사일 평균가격과 1~4주 전 가격 추이.
- `15064971`: 지역·품종·시험년도별 벼 작황과 생육 성적.
- `15078194`: 시간별 기온·강수·일사·토양 온도/수분을 포함한 농업기상 관측.
- `15106661`: 축산물 부위·국가별 월/상중하순 수입량.

이 조합은 단순 시세 조회가 아니라 “기상·작황·수입 공급을 이용한 가격 선행예측”이라는 서비스 기획으로 이어진다. 이것이 이번 평가에서 단순 precision 상승보다 더 중요한 효과다.

### 재활용·불용품: 흔한 단어의 오염을 이겨냄

Q10의 lexical 첫 페이지는 관광자원·수자원처럼 “자원”만 우연히 맞는 항목이 섞여 P@10 0.30이었다. HV는 다음을 찾았다.

- `15156640`: 8개 권역, 폐지·플라스틱·유리·금속·타이어 등 26개 재활용자원의 월별 원/kg 가격.
- `15141652`: 폐가전·폐휴대폰·폐자동차 수거처와 수거비용.
- `15157738`: 온비드 정부재산 중 불용품 목록.
- `15043362`: 공매일자·유찰횟수·감정가·최저공매가가 있는 공매자산 정보.

가격 차익, 회수 물류, 공급원 발굴을 각각 별도 제품 기능으로 연결할 수 있다.

### 안전·운영: 사용자 표현에는 없던 공식 위험 신호

Q5의 HV는 L top 10에 없던 `15076352 한국환경공단_전기자동차 충전소 정보`를 2위에서 찾았다. 공식 설명상 충전기 상태, 상태갱신일시, 마지막 충전 시작/종료일시 등을 제공하므로 차량 운영 중단 감시에 직접 쓸 수 있다.

Q6의 HV는 `15095149 기상청_영향예보`와 `15139182 건설현장 안전 신호등`을 각각 폭염 예측과 현장 위험 축에서 찾았다. 전자는 폭염 위험 수준과 분야별 대응 요령, 후자는 진행 중인 중·소규모 건설현장의 최근 기술지도 결과를 제공한다. 일반 검색의 “폭염 일수”만으로는 만들기 어려운 지역·현장별 경보 서비스가 가능해진다.

### 돈이 되는 공고: 검색축은 필수지만 ranking 보정도 필요

Q4의 HV는 `15157820 중소기업 지원사업 공고`, `15125364 K-Startup`, `15129394 나라장터 입찰공고`, `15129456 누리장터 민간입찰공고`를 한 페이지에서 찾았다. 이는 “받을 수 있는 돈과 사업 기회”를 지원금과 매출 기회로 나눠 보는 좋은 사례다.

하지만 PL은 같은 쿼리에서 P@10 0.80, HV는 0.50이었다. 의미적으로 비슷한 기업정보·수혜기업·연구과제 이력이 공고를 밀어냈기 때문이다. 하이브리드가 평균적으로 좋다는 사실과 별개로, `공고`, `입찰`, `상태`처럼 실행 의미가 강한 단어는 exact lexical 결과를 최소 1~2개 보장해야 한다.

## 실행 비용과 모델 선택

측정 환경은 Mac Studio, Apple M4 Max 16코어, 메모리 64GB다. 사용자의 컴퓨터가 일반 사용자보다 고사양이므로 절대 지연시간은 보급형 PC 성능으로 일반화하면 안 된다.

| 항목 | 측정값 |
|---|---:|
| 카탈로그 | 11,902건, JSON 약 11MB |
| REST 검색 대상 | 7,130건 |
| 의미 인덱스 | 11,902 × 768, gob 약 51MB |
| Ollama | 0.33.2 |
| 모델 | `embeddinggemma:300m-qat-q4_0`, 약 239MB |
| warm L 10회 | 0.94초, 평균 약 94ms |
| warm V 10회 | 3.00초, 평균 약 300ms |
| warm HV 10회 | 5.63초, 평균 약 563ms |

위 시간에는 매번 별도 CLI 프로세스 시작, 약 11MB 카탈로그 및 의미 인덱스 로드, 검색이 모두 포함된다. 모델 최초 다운로드와 인덱스 최초 구축 시간은 이 측정에서 제외했다.

[Ollama 공식 문서](https://docs.ollama.com/api/introduction)는 설치 후 기본 로컬 API를 `http://localhost:11434/api`에 제공한다고 명시한다. `/api/embed`는 문자열 배열 입력과 L2 정규화된 벡터를 제공하며 같은 모델로 문서와 질의를 임베딩하고 cosine similarity를 쓰는 것을 권장한다. [Ollama embeddings 문서](https://docs.ollama.com/capabilities/embeddings)와 현재 구현 방식이 일치한다.

[Google EmbeddingGemma 모델 카드](https://ai.google.dev/gemma/docs/embeddinggemma/model_card)는 이 모델이 100개 이상 언어로 학습된 검색/검색결과 회수용 모델이며, 최대 2K 토큰과 기본 768차원을 제공한다고 설명한다. 문서에는 `title: ... | text: ...`, 질의에는 `task: search result | query: ...` prefix를 권장하며 현재 구현도 이 형식을 사용한다. 일반 sentence similarity prefix는 retrieval 용도가 아니라고 명시돼 있다.

Q4 모델은 합리적인 기본값이다. 공식 다국어 MTEB 평균은 full precision 768d 61.15, Q8 60.93, Q4 60.62로 차이가 작고, [Ollama 공식 모델 태그](https://ollama.com/library/embeddinggemma/tags)에서 Q4 다운로드는 239MB, Q8은 338MB, BF16/latest는 622MB다. 고사양 컴퓨터라 BF16도 실행 가능하지만, 이 한국 공공데이터 쿼리셋에서 독립 gold label로 이득을 확인하기 전에는 기본 설치 부담을 2.6배 키울 이유가 부족하다.

Ollama `/api/embed`의 `truncate` 기본값은 true이며 컨텍스트 초과 입력을 자동으로 자른다([API 명세](https://docs.ollama.com/api/embed)). 현재 카탈로그에서 문자 수가 가장 긴 문서를 `truncate:false`로 실제 임베딩했을 때 1,192토큰으로 2K 한도 안이었다. 전 문서의 토큰 길이를 완전 조사한 것은 아니므로, 향후 상세 명세까지 색인할 때는 `truncate:false`와 명시적 chunking으로 조용한 정보 손실을 막아야 한다.

Google은 768차원을 512/256/128로 앞에서 잘라 재정규화하는 MRL을 지원하며, 공식 다국어 점수는 768d 61.15에서 256d 59.68로 감소한다. 별도 벡터 DB 전에 256차원 인덱스가 한국어 P@10/recall을 얼마나 유지하면서 파일과 scan 비용을 줄이는지 먼저 절제 실험하는 편이 낫다.

## 제품 및 구조 권고

### 1. 지금은 벡터 DB를 추가하지 않는다

현재 11.9k 건에서는 단순 cosine full scan과 로컬 파일이 충분히 작고 운영 의존성이 없다. 다음 중 하나가 실제 측정될 때 ANN/vector DB를 검토한다.

- 카탈로그가 현재보다 한 자릿수 이상 커져 scan이 사용자 지연의 주원인이 될 때.
- 다수 사용자가 동시에 질의하는 상시 서버가 되어 인덱스 중복 로드가 문제가 될 때.
- 복잡한 메타데이터 필터와 증분 업데이트를 인덱스 엔진에 맡겨야 할 때.

그 전에는 provider/index 인터페이스를 유지하되 flat index를 쓰는 편이 설치 한 번이라는 제품 목표에 맞다.

### 2. MCP에서는 모델 계획을 기본 진입점으로 유지한다

CLI 원문 검색은 LLM을 내장하지 않으므로 concepts 없는 V까지만 자동 수행한다. 반면 MCP 호스트 모델은 사용자의 목표를 다음과 같은 2~8개 데이터 축으로 바꿀 수 있다.

- 직접 대상: 지원사업 공고, 공매 물건.
- 수요/시장: 매출, 방문자, 유동인구.
- 선행지표: 작황, 기상, 수입량.
- 공급/운영: 회수처, 충전기 상태, 공실.
- 위험/제약: 온열질환, 현장 안전, 규제.

동의어만 나열하면 축 다양성이 생기지 않는다. 원문 의도를 보존하고 위 관점들을 필요에 따라 조합해야 한다.

### 3. exact lexical 보호 장치를 추가한다

현재 평균은 HV가 가장 좋지만 Q4 같은 실패가 있다. 축별로 다음 순서를 권한다.

1. 제목/기관/설명에서 모든 핵심어가 맞는 strict lexical 결과 1개를 먼저 확보.
2. semantic 결과로 표현 차이와 설명 기반 recall을 보충.
3. 같은 API 계열이 페이지를 독점하지 않도록 축별 round-robin.
4. `공고`, `입찰`, `실시간 상태`, `가격`처럼 실행 객체가 명시된 경우 그 객체가 없는 후보를 감점.

이는 룰 기반 동의어 사전을 늘리자는 뜻이 아니라, 검색축의 명시적 의도를 ranking 제약으로 쓰자는 뜻이다.

평가 직후 이 권고를 구현했다. 계획형 하이브리드 검색은 이제 각 명시적 검색축에서 모든 핵심어가
일치한 첫 lexical 결과 한 건을 semantic 확장보다 먼저 보장한다. 이 변경은 위 표를 만든 뒤 적용됐으므로
표의 수치는 변경 전 기준선으로 남겨 두었으며, 다음 gold set에서 효과를 다시 측정해야 한다.

### 4. 설명 다음 단계로 endpoint/parameter 색인을 점진적으로 만든다

현재 의미 인덱스는 카탈로그의 제목·기관·분류·공식 설명을 사용한다. 사용자가 우려한 대로 설명이 빈약하거나 실제 operation 이름에만 중요한 개념이 있으면 검색할 수 없다.

전체 endpoint를 한 번에 모델 컨텍스트로 넣을 필요는 없다. `catalog_search → describe_api → call_api` 구조를 유지하면서:

- describe된 API의 operation 이름, 기능 설명, 요청/응답 변수만 별도 로컬 캐시에 누적한다.
- 첫 단계는 카탈로그 entry를 찾고, 두 번째 단계는 후보 내부 operation을 재검색한다.
- 실제로 조회된 상세만 점진적으로 색인해 포털 부하와 초기 구축 시간을 제한한다.

이렇게 하면 카탈로그 검색은 넓은 발견을, 상세 검색은 실제 호출 가능성 확인을 담당한다.

### 5. 릴리즈 뒤 실제 사용자 로그로 gold set을 만든다

이번 10개 × top 10 평가는 방향을 결정하기에는 충분하지만 최종 ranking 튜닝에는 작다. 다음 평가판은 개인정보 없이 사용자 목표, 선택한 PK, describe 진입 여부, 실제 call 성공 여부를 사용해 50~100개 쿼리와 최소 2명의 독립 판정자로 만든다.

권장 지표는 다음과 같다.

- Precision@5/10: 첫 화면의 잡음.
- Recall@20 또는 pooled recall: 숨어 있던 관련 API 회수.
- nDCG@10: 매우 유용/보조/무관의 등급 순위.
- Intent-axis coverage: 가격·수요·공급·위험 등 서비스 기획 입력의 범위.
- Describe success와 Call success: 관련해 보여도 실제 명세/호출이 되는지.

[EmbeddingGemma 모델 카드의 한계](https://ai.google.dev/gemma/docs/embeddinggemma/model_card)는 학습 데이터의 편향·도메인 공백과 자연어의 미묘한 뉘앙스 이해 한계를 명시하고 지속적인 지표 및 사람 검토를 권고한다. 따라서 semantic-only로 단순화하지 않고 hybrid와 실제 한국 공공데이터 평가를 계속 유지해야 한다.

## 재현 방법

평가 바이너리는 현재 작업 트리에서 만들었다.

```bash
go build -o /tmp/gongctl-semantic-bench ./cmd/gongctl
/tmp/gongctl-semantic-bench catalog info --format json
ollama --version
```

각 쿼리는 다음 세 명령으로 비교했다.

```bash
q='동네에 새 가게를 열었을 때 잘될 자리를 찾고 싶다'

/tmp/gongctl-semantic-bench catalog search "$q" \
  --limit 10 --rest-only --semantic=false --format json

/tmp/gongctl-semantic-bench catalog search "$q" \
  --limit 10 --rest-only --semantic=true --format json

/tmp/gongctl-semantic-bench catalog search "$q" \
  --limit 10 --rest-only --semantic=true --format json \
  --concept '상권 업종별 매출' \
  --concept '유동인구 생활인구' \
  --concept '사업체 개업 폐업' \
  --concept '상가 임대료 공실'
```

PL 절제 실험은 마지막 명령의 `--semantic=true`만 `--semantic=false`로 바꿨다.
