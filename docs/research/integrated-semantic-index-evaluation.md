# API + FILE 통합 시맨틱 인덱스 평가

평가일: 2026-09-01

## 결론

95,951건 통합 카탈로그의 시맨틱 검색은 일반적인 개인용 컴퓨터에서도 실행 가능한 범위다. 다만 최초
전체 임베딩은 기준 Mac Studio에서도 17분 44초가 걸렸고, 검색 한 번은 키워드 검색보다 약 2초 느렸다.
따라서 Ollama와 로컬 시맨틱 인덱스를 모든 사용자의 필수 설치로 만들 근거는 없다.

품질 이득은 질문 유형에 따라 달랐다. 정확한 데이터 명칭을 모르는 자연어 질문에서는 관련 후보가
앞으로 이동했다. 특히 에이전트가 질문을 서로 다른 검색축으로 나눈 뒤 시맨틱 검색을 결합하자, 축별
데이터뿐 아니라 두 축이 이미 연결된 상관·분석 데이터까지 발견했다. 반면 검색축 계획 없이 원문만
임베딩하면 한 주제에 결과가 몰리거나 관련 없는 후보가 섞였다.

현재 권장 경로는 다음과 같다.

- 기본: MCP host 또는 `catalog discover`가 만든 검색축으로 lexical 검색
- 선택: 표현 차이와 설명 기반 recall이 중요한 반복 탐색에서 Ollama hybrid 검색 추가
- 비권장: semantic-only 결과를 연결 가능성이나 사업성의 증거로 사용

## 측정 환경

| 항목 | 값 |
|---|---|
| 컴퓨터 | Mac Studio, Apple M4 Max 16-core, 64GB RAM |
| Ollama | 0.33.2 |
| 모델 | `embeddinggemma:300m-qat-q4_0`, 약 238MB |
| 카탈로그 | 95,951건: REST 7,132, LINK 4,766, FILE 84,047, 미확인 6 |
| `catalog.json` | 104,750,727 bytes, 약 99.9MiB |
| v1 의미 인덱스 | 434,041,030 bytes, 약 413.9MiB |
| v2 의미 인덱스 | 440,277,910 bytes, 약 419.9MiB |
| 벡터 | 768차원 float32, exact flat cosine scan |

명령마다 별도 CLI 프로세스를 시작했다. 따라서 검색 시간과 최대 메모리에는 카탈로그·인덱스 파일
로드가 포함된다. Ollama 모델은 이미 다운로드되고 실행 중인 warm 상태였다.

## 구축 및 갱신 비용

### 최초 전체 빌드

```text
의미 인덱스 95951건 저장 · 1064.1초
wall time 1064.54초
OpenDataCTL maximum resident set size 약 2.53GiB
관찰된 Ollama llama-server RSS 약 1.57GiB
```

두 프로세스의 최고점이 정확히 같은 순간이었다고 보장할 수 없으므로 단순 합계는 근사치다. 보수적으로
보면 전체 작업은 약 4.1GiB 수준의 메모리 여유가 필요했다. 운영체제와 다른 프로그램까지 고려하면
8GB는 가능한 하한이고, 16GB를 권장 사양으로 두는 편이 안전하다.

### v1에서 문서 hash 기반 v2로 갱신

동일한 카탈로그와 모델로 다시 실행했을 때 95,951개 벡터를 모두 재사용했다.

```text
의미 인덱스 95951건 저장 · 재사용 95951 · 새 임베딩 0 · 1.9초
wall time 2.87초
maximum resident set size 약 2.86GiB
```

재임베딩 시간은 제거됐지만 현재 gob 파일을 읽고 다시 쓰는 동안 메모리 사용량은 여전히 크다. 이
수치는 증분 임베딩만으로 최종 사용자 경험이 완성되지 않으며, packed vector와 mmap reader가 다음
저장 형식 후보인 이유다.

## 검색 비용

세 자연어 질의를 각각 키워드와 hybrid로 실행했다.

| 질의 | 키워드 | hybrid | 키워드 최대 RSS | hybrid 최대 RSS |
|---|---:|---:|---:|---:|
| 시세보다 싸게 살 투자 물건 | 1.03초 | 2.96초 | 약 341MiB | 약 1.63GiB |
| 돌봄시설을 인수할 지역 | 0.96초 | 2.84초 | 약 327MiB | 약 1.63GiB |
| 비와 업종·지역 매출 | 1.07초 | 2.94초 | 약 329MiB | 약 1.63GiB |

두 개의 명시적 검색축을 함께 준 교차 분야 질의는 다음과 같았다.

```text
원문: 비가 많이 오면 매출이 떨어질 업종과 지역을 찾고 싶어
검색축 1: 강수량 기상 관측
검색축 2: 업종별 지역 매출
```

계획형 lexical은 1.29초, 계획형 hybrid는 4.60초였다. hybrid는 원문과 두 검색축을 각각 임베딩하고
95,951개 벡터를 여러 번 평면 검색하므로 단일 원문보다 오래 걸린다.

릴리즈 전 성능 검토에서 계획 검색이 축별 전체 `Hit`를 보관하고, semantic 검색이 질의별 전체 `Hit`를
정렬한 뒤 잘라내는 메모리 병목을 확인했다. 전수 점수와 정확한 순위 기준은 유지하면서 top-K heap과
bounded candidate materialization으로 바꾼 뒤 같은 계획형 hybrid 질의를 두 번 다시 실행한 결과는
2.51~3.53초, 최대 RSS 약 1.62GiB였다. RSS는 768차원 gob 인덱스 로드가 지배해 크게 줄지 않았지만 다축 검색의
추가 `Hit` 배열은 제거됐다. 상위 결과에는 이전 평가에서 유효하다고 본 다음 결합 데이터가 그대로
포함됐다.

- `상권별업종별 이용률-기상현황-유동인구 상관계수 테이블(강수없음)`
- `상권별업종별 이용률-기상현황-유동인구 분석 기초자료(강수있음)`

별도의 95,951행 in-process 회귀 benchmark에서 최대 허용치인 8축 계획 검색은 0.294초/약 47.6MiB
allocation, 8차원 synthetic semantic top-400 선택은 0.0033초/약 3.5MiB allocation이었다. 후자는 768차원 dot-product
속도를 대표하는 수치가 아니라, 전체 `Hit`를 만들지 않는 선택기 자체의 상한을 검증하는 용도다.
semantic top-K는 같은 입력을 전수 정렬한 결과와 PK·점수가 순위별로 완전히 일치하는 테스트를 둔다.

## 결과 품질 스모크 비교

이 평가는 독립 판정자가 만든 gold set이 아니라 실제 결과를 수동 확인한 소규모 스모크 테스트다.
정식 Recall@10이나 nDCG@10 수치로 해석하면 안 된다.

### 시세보다 싸게 살 수 있는 물건을 찾아 투자하고 싶어

키워드 상위 10건은 농촌교육농장, 농업기술, 농기계, 지방세 등으로 구성됐고 직접적인 공매 물건은
없었다. hybrid는 `한국자산관리공사_차세대 온비드 순위물건목록 저감률순위 조회서비스`를 1위로
올렸다. 예금보험공사의 파산금융회사 매물 투자 안내집도 새로 회수했다. 다만 농업 데이터가 교차
노출돼 첫 화면 노이즈가 완전히 사라지지는 않았다.

### 어르신 돌봄시설을 인수할 지역을 고르고 싶어

키워드 결과에는 무료급식소·일자리·지역아동센터가 상위에 많았다. hybrid 상위 10건에는 다음 직접
후보가 들어왔다.

- 어르신 복지시설 현황
- 노인복지시설 현황
- 노인요양복지시설
- 노인요양 공동생활가정
- 노인요양시설 현황

지역아동센터 노이즈도 남았으므로 시맨틱 유사도만으로 시설 유형을 확정하면 안 된다.

### 비가 많이 오면 매출이 떨어질 업종과 지역을 찾고 싶어

원문만 검색했을 때 lexical과 hybrid 모두 매출 데이터에 집중해 기상 축을 충분히 회수하지 못했다.
두 검색축을 명시하자 lexical도 강수량과 매출 데이터를 번갈아 반환했다. hybrid는 여기에 더해 키워드
상위 결과에서 보이지 않던 다음 연결 데이터를 직접 발견했다.

- `서울특별시 서대문구_상권별업종별 이용률-기상현황-유동인구 상관계수 테이블(강수없음)`
- `서울특별시 서대문구_상권별업종별 이용률-기상현황-유동인구 분석 기초자료(강수있음)`
- `서울특별시 서대문구_상권별업종별 이용률-기상현황 분석 기초자료(강수있음)`

이 사례는 시맨틱 검색의 가장 설득력 있는 가치가 단순 동의어 검색이 아니라, 모델 계획으로 분리된
축과 공식 설명을 함께 사용해 이미 존재하는 교차 분야 자료를 회수하는 데 있음을 보여준다.

## 제품 판단

현 시점에서 Ollama를 필수 요구사항으로 만들지 않는다.

- MCP 사용자는 Codex·Claude·Gemini·Cursor가 검색축을 계획할 수 있어 lexical만으로도 기본 발견
  흐름을 사용할 수 있다.
- 시맨틱은 정확한 명칭을 모르는 broad-intent 질문과 교차 분야 탐색에서 유의미한 추가 결과를 만들었다.
- 시맨틱 원문 검색만으로는 축 다양성을 보장하지 않으며 노이즈도 남는다.
- 최초 빌드 17분 44초는 일반 사용자에게 그대로 요구하기 어렵다.
- 로컬 갱신은 문서 hash 재사용으로 1.9초까지 줄었지만, 첫 설치는 공식 prebuilt bundle이 필요하다.

적극 권장 여부는 향후 동일 snapshot의 봉인 질의에서 Recall@10, nDCG@10, 직접 관련 결과 비율과 심각한
노이즈 수를 측정한 뒤 결정한다. 배포 방식과 유사 오픈소스의 근거는
[시맨틱 인덱스 배포·갱신 조사](semantic-index-distribution.md)를 따른다.

## 재현 명령

```bash
opendatactl catalog sync --type ALL --per-page 200
opendatactl catalog semantic-build --pull=false --batch-size 32

opendatactl catalog search "시세보다 싸게 살 수 있는 물건을 찾아 투자하고 싶어" \
  --limit 10 --semantic=false --format json
opendatactl catalog search "시세보다 싸게 살 수 있는 물건을 찾아 투자하고 싶어" \
  --limit 10 --semantic=true --format json

opendatactl catalog search "비가 많이 오면 매출이 떨어질 업종과 지역을 찾고 싶어" \
  --limit 12 --concept "강수량 기상 관측" --concept "업종별 지역 매출" \
  --semantic=true --format json
```
