# Karpathy 원문에서 가져올 설계 원칙

조사일: 2026-09-08. 상태: 연구 제안; 제품 구현·성능 검증 아님.
기준은 [INTENT.md](../../INTENT.md)이며, Andrej Karpathy의 글과 직접 관리하는 저장소를 참고한다.
아래 `원문 사실`과 `오데덕 적용 추론`을 구분한다. 그의 관점이 오데덕의 특정 아키텍처를 검증한 것은 아니다.

## 1. Software 2.0: 행동을 명시하는 자료와 평가

**원문 사실.** 2017년 글은 사람이 명령을 작성하는 Software 1.0과, 데이터·구조·목표에 따라
최적화로 가중치를 얻는 Software 2.0을 구분한다. 원하는 행동을 정의하는 데이터의 수집·수정·정제가
개발의 중요한 부분이 된다는 주장이다. 동시에 모델 내부를 설명하기 어렵고, 편향과 조용한 실패가
생길 수 있다고 경고한다. 반복 평가가 가능하고 명시적 알고리즘 작성이 어려운 문제를 주요 적용
대상으로 제시한다. [Software 2.0, 2017-11-11](https://karpathy.medium.com/software-2-0-a64152b37c35)

**오데덕 적용 추론.** 분야별 검색어와 정답 경로를 계속 하드코딩하기보다, 다음 행동을 선택하는
모델과 이를 평가하는 목표 사례를 개선한다. 그러나 이 글은 모든 기능을 LLM에 넘기라는 근거가
아니다. 인증키 격리, 공식 호출 계약, 행 변환, 중복 집계 방지, 출처 연결은 명시적으로 검사 가능한
코드로 유지할 이유가 있다. 다음은 제안하는 책임 경계다.

| 모델에 맡길 후보 판단 | 실행 코드가 확인할 계약 |
| --- | --- |
| 목표에 필요한 관측 역할과 낯선 분야의 후보 | 실제 제공형·필드·접근 가능성 |
| 중간 대응표, 개념·필드 매핑 가설 | 식별자 namespace, 단위·grain·시간의 호환성과 근거 |
| 실패 관찰에 따른 다음 탐색 행동 | 권한·호출 범위·자원 예산 |
| 분석 결과의 의미와 사업 가설 | 재현 가능한 계산·출처·관측 범위; 사실과 가설의 구분 |

이 경계 자체는 신경망 학습 구현 제안이 아니다. 현재 사용하는 모델의 교체·프롬프트·탐색 정책을
비교할 때도 같은 목표 평가를 사용할 수 있다는 추론이다. 의미 매핑 후보의 생성과 사실 승인을
한 단계로 합치지 않는다.

## 2. micrograd: 이해 가능한 핵심과 별도의 정답 기준

**원문 사실.** micrograd는 스칼라 연산의 동적 DAG와 역전파를 작은 엔진으로 구현하며 교육 용도를
명시한다. 엔진은 값과 선행 연산을 보존하고 위상 순서의 역방향으로 미분을 전파한다. 테스트는
같은 식을 PyTorch에서도 계산하여 결과와 기울기를 비교한다.
[README](https://github.com/karpathy/micrograd),
[engine.py](https://github.com/karpathy/micrograd/blob/master/micrograd/engine.py),
[test_engine.py](https://github.com/karpathy/micrograd/blob/master/test/test_engine.py)

**오데덕 적용 추론.** 모델 제안 → 실제 관측 → 검사 → 변환 → 산출물의 핵심 경로를 개발자가
읽고 재실행할 수 있게 만든다. 한 단계의 성공을 다음 단계의 사실 승인으로 오해하지 않도록
중간 결과의 타입과 provenance를 보존한다. 평가의 정답은 엔진이 자신의 성공 메시지를 내는지가
아니라, 독립적으로 검토한 원천과 기대 산출물이어야 한다.

**범위 한계.** micrograd의 그래프는 미분 계산 그래프다. 이를 공공데이터 entity graph나 온톨로지의
효용 증거로 인용할 수 없다. 코드 줄 수가 적다는 이유로 대규모 저장·동시성·보안·운영 문제가
해결된다고 볼 수도 없다.

## 3. nanoGPT와 microgpt: 핵심 알고리즘과 운영 최적화를 구분

**원문 사실.** nanoGPT는 읽고 수정하기 쉬운 학습 루프와 모델 정의를 강조한다. README에는 기준
모델과의 비교, 학습 데이터의 차이 때문에 생기는 비교 한계도 있다. 현재 README의 2025년 11월
공지에서는 nanoGPT를 deprecated로 표시하고 nanochat을 안내한다. 여기서는 역사적 설계 사례로만
참조하며 신규 제품 의존성으로 추천하지 않는다. [nanoGPT README](https://github.com/karpathy/nanoGPT)

2026년 microgpt 글은 GPT의 학습·추론을 의존성 없는 작은 Python 파일로 드러내는 프로젝트를
설명한다. 스칼라 autograd의 알고리즘과 효율적인 텐서 구현을 구분하며, 작은 구현이 훨씬 비효율적임을
명시한다. [microgpt, 2026-02-12](https://karpathy.github.io/2026/02/12/microgpt/)

**오데덕 적용 추론.** 범용성을 대형 프레임워크의 개수로 표현하기보다, 작은 공통 연산과 명확한
입출력 계약으로 여러 목표를 처리할 수 있는지 확인한다. 필요한 성능·저장 기능은 측정된 병목에
따라 추가한다. 이것은 모든 것을 단일 파일에 쓰거나 운영용 라이브러리를 직접 재구현하자는 뜻이
아니다. 포털 취약 지점과 인증 경계는 알고리즘 설명을 위해 지워도 되는 부수 요소가 아니다.

## 4. INTENT에 맞는 적용 순서

1. 키워드·PK가 없는 실제 목표와 독립적인 기대 산출물을 먼저 고정한다. 한 사례의 성공만으로
   일반화하지 않고 분야·제공기관을 분리한 평가를 둔다.
2. 읽고 재실행할 수 있는 공통 실행 경로를 만든다. 단일 원천 답변, 집계·비교, 교차 원천 연결,
   가설 발견을 모두 검증 대상으로 삼는다.
3. 실패를 코드 계약 오류, 관측 부족, 의미 해석 오류, 탐색 정책 오류로 구분한다. 모든 실패를
   새 온톨로지 클래스나 사례별 분기로 해결하지 않는다.
4. 모델·의미 계약·검색 방식의 변경을 같은 평가와 비용으로 비교한다. 사업 브레인스토밍은
   우선 활용처가 될 수 있지만, 구매자·매출 가정을 원천 데이터의 사실로 승인하지 않는다.

위 순서는 본 조사에서 제안한 오데덕 설계다. Karpathy가 온톨로지·GraphRAG의 도입 또는 배제를
권고했다고 해석하지 않는다. 해당 기술의 판단은 별도의 원천·질문·실패 사례와 실험에 근거해야 한다.
