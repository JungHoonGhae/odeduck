# 교차 데이터 연결 발견 v1 출시 전 평가

평가일: 2026-08-31

카탈로그: data.go.kr OpenAPI 11,902건

계획 모델: 로그인된 Codex CLI

검색기: 로컬 lexical + `embeddinggemma:300m-qat-q4_0` flat vector index

## 평가 질문

검색 역할별 1위 결과를 자동으로 연결 카드로 만드는 방식보다, 실제 검색 결과의 제목과 공식
설명 미리보기를 다시 읽고 PK를 명시적으로 선택하는 precision gate가 약한 연결을 줄이는가?

이번 평가는 세 개의 실제 자연어 목표를 같은 구현으로 실행한 출시 전 수동 감사다. baseline은
두 번째 검색 결과에서 각 역할의 첫 항목을 순서대로 최대 3개 취하는, 구현 중 제거한 자동 선택
방식이다. treatment는 같은 결과 집합을 본 모델이 최대 3개 PK를 고르고 서버 hard gate를 통과한
카드다. treatment에는 추가 모델 호출 한 번이 필요하므로 동일 비용의 통계 실험은 아니다.
표본도 세 건뿐이어서 일반적인 정확도 수치로 홍보하지 않는다.

판정에서 `pass`는 제목·공식 preview가 역할과 새 payload를 직접 뒷받침하고, 지역·대상 범위가
조건부라면 그 제한을 명시할 수 있다는 뜻이다. 실제 field 호환이나 값 join을 증명했다는 뜻은
아니다. `fail`은 검색어 일부만 맞아 역할 자체를 뒷받침하지 못하는 경우다.

## 결과

| 목표 | 자동 1위 3개 수동 판정 | precision gate가 선택한 3개 | 관찰 |
| --- | --- | --- | --- |
| 저렴한 공매 부동산의 숨은 위험과 실제 수요 | 1/3 pass. 분양권 전매가격을 권리인수 위험으로, 전북 임대아파트 보증금을 점유 위험으로 고른 결과는 역할 불일치 | 아파트 실거래가, 부산 상권 변화지표, 부산 토양오염실태 | 가격·상업 수요·환경 위험으로 역할이 갈라졌고 아파트/부산/조사지점 한계를 모두 명시 |
| 소상공인 폐업 위험 지역과 지원 우선순위 | 2/3 pass. 법정동 매핑과 쇠퇴지표는 유효하지만 상가정보 API는 업종 코드 연계표 역할을 직접 뒷받침하지 못함 | 부산 점포이력, 국토부 쇠퇴진단 지표, 부산 상권 변화지표 | 폐업 이력·지역 취약성·상권 안정성으로 다른 payload를 선택하고 부산 범위를 명시 |
| 폭염 취약 고령자 이동 돌봄 배치 | 2/3 pass. 법정동 코드는 유효하고 위성 산출물은 잠재적이나, 장비 업체 정보는 실내 노출 이벤트가 아님 | 응급안전안심 대상자, 지역별 온열질환자, 주요 도시 폭염 일수 | 돌봄 수요·건강 피해·노출을 분리하고 서비스 등록자 편향과 거친 공간 단위를 명시 |

세 질의의 baseline 첫 3개 중 메타데이터 계약을 통과한 것은 5/9, treatment 카드는 9/9였다.
이는 **추가 선택 단계가 이 표본의 후보 정밀도를 개선했다**는 근거이지, 9개 API pair가 실제로
join된다는 근거는 아니다. 전체 실행 시간은 각 약 97~108초였고 대부분 세 차례 agent CLI
호출에서 발생했다. MCP 경로에서는 대화 중인 호스트 모델이 같은 세 번의 `catalog_search` 호출을
계획하므로 하위 CLI 프로세스를 실행하지 않는다.

## 새로 발견된 연결과 일반 검색의 차이

공매 질의의 직접 키워드는 공매·실거래·입찰·건축물·토지 규제를 찾았다. 실제 결과를 본 뒤의
Bridge 확장은 상권 변화와 토양오염 조사처럼 제목에 공매가 전혀 없는 데이터를 회수했다. 이 둘은
각각 상업용 물건의 주변 영업 지속성과 토지·공장 주변 환경 위험이라는 다른 판단을 제공한다.
일반적인 한 문장 lexical 검색으로는 공통 단어가 없어 같은 결과 목록에 들어오기 어렵다.

소상공인 질의에서는 현재 점포 분포만 보는 대신 점포의 개·폐업 이력, 도시 쇠퇴진단, 평균
생존·폐업 개월수를 연결 후보로 만들었다. 폭염 질의에서는 고령인구만 세는 대신 서비스에 실제로
등록된 대상자, 과거 온열질환자, 도시별 폭염 일수를 서로 다른 역할로 분리했다. 의미 벡터는 표현이
다른 후보를 회수하는 데 도움을 주었지만, 어떤 항목도 벡터 점수만으로 카드가 되지는 않았다.

## 발견한 한계

- 지역 coverage가 가장 큰 위험이다. 전국 질문에서도 부산처럼 metadata가 풍부한 지역 API가
  Anchor 또는 Bridge로 뽑힐 수 있다. v1은 이를 거부하기보다 `candidateEvidence`에 조건을 쓰고,
  후속 명세·표본 검증 전에는 전국 결과로 일반화하지 않는다.
- 제목과 preview에는 출력 field, code-system version, 공간·시간 grain이 충분히 없다. 따라서 검색
  계층의 유일한 상태는 `candidate`다.
- 추가 모델 선택은 품질과 맞바꾼 지연이다. 독립 CLI에서 약 1.5~2분이 걸릴 수 있으며, 빠른 단일
  API 검색은 `catalog search`를 사용해야 한다.
- 같은 호출 예산의 봉인된 benchmark, 두 명 이상의 blind 평가, no-connection 실제 질의 표본은
  후속 평가다. 현재 수치는 제품 설명의 성능 주장으로 쓰지 않는다.
- data.go.kr 로그인 세션이 없는 환경에서는 실제 활용신청과 두 API의 공통 slice 호출을 재현하지
  못했다. Onbid API 명세는 확인했지만 값 교집합은 `sample_verified`로 승격하지 않았다.

## 채택 결정

v1에는 post-retrieval precision gate를 채택한다. 검색 1위를 자동 카드로 만드는 코드는 두지 않는다.
서버는 다음 조건을 모두 만족한 명시적 selection만 `candidate`로 반환한다.

1. 선택 PK가 **현재 반환된 hits 안에 존재**한다.
2. 역할, Incremental Value, 후보 근거, edge kind, 예상 결합키가 모두 있다.
3. proxy edge에는 변환과 손실 설명이 있다.
4. 역할과 PK를 중복하지 않고 전체 카드는 최대 3개다.
5. 통과하는 항목이 없으면 Abstention한다.

강한 상태는 검색 결과가 아니라 `describe_api`와 공통 지역·기간의 `call_api` 응답 profile을 비교한
호스트만 주장할 수 있다. 이 경계가 지켜지는 한 현재 카탈로그와 선택적 Ollama만으로 v1을 출시하며,
전역 관계 그래프나 vector DB는 도입하지 않는다.

이 사례가 설명하는 가치는 공매라는 단어와 가까운 결과 외에도 상권·환경처럼 다른 역할의 자료를
찾아 함께 검토할 이유를 제시한다는 것이다. 이용자의 실제 발언을 인용하거나, 새로 수행한 무힌트
탐색·복수 API 신청·결합의 성공 화면을 재현한 것은 아니다.

서로 다른 범위·시점의 자료를 같은 물건의 사실처럼 합치지 않는다.

### 병목과 현재 기능을 연결하는 표현

| 사용자에게 막히는 일 | README에서 보여주는 오데덕의 역할 | 근거·범위 |
| --- | --- | --- |
| 어떤 검색어와 분야를 골라야 할지 모름 | 질문을 여러 역할로 넓혀 뜻밖의 자료도 후보로 탐색 | 이 문서의 실제 발견 결과, [의미 검색 평가](semantic-search-evaluation.md) |
| API·파일 설명과 필요한 항목을 따로 확인 | 실제 명세·지원 파일 항목을 검사 | 위 `inspect` 기록. 의미가 맞는 최종 결합을 보장하지 않음 |
| 필요한 서비스마다 신청하고 승인 확인 | MCP 대화에서 미신청 API의 신청·승인 확인·조회 연결 | [고정된 경쟁 감사](competitive-workflow-audit.md), [실계정 신청·호출 기록](../promo/odeduck-agent-explainer.md). 모든 대안이 수동이라는 주장은 하지 않음 |
| 인증키의 위치·형태와 호출 설정을 챙김 | 계정 키를 재사용해 내부 주입 | `internal/portal/apikey.go`, `internal/apicall/call.go`, `internal/mcpserver/guide.go`. data.go.kr 일반 키는 계정 단위이고 외부 provider 키는 별도 |
| 자료를 모아도 어떻게 함께 볼지 막막함 | 각 자료의 역할·연결 이유·출처와 확인할 점 제시 | 발견은 검증됨. 실제 연결·계산과 범용 목표 완주는 [실험 기능의 범위](../advanced-usage.md#목표에서-결과까지-실행하기--experimental)를 따름 |

그림의 가지는 한 요청 안에서 필요한 여러 데이터 역할을 나타낸다. 동시 신청 기능이나,
이 세 원천의 실제 결합·투자 판단이 완료됐다는 뜻으로 사용하지 않는다.
사람의 로그인, 사용하는 AI 앱의 실행 승인 설정, 제공기관 심의·트래픽 조건은 유지된다.
출력 시간을 줄였다는 수치나 수익·손실 감소 효과는 측정하지 않았으므로 주장하지 않는다.

### 절차와 결과를 설명하는 별도 슬라이드

[기존 절차의 병목](../assets/odeduck-manual-bottlenecks.html)은 검색어 재시도, 서비스별 신청·승인 확인,
키 입력 방식과 호출 설정의 반복을 시각화한다. 위 표의 제품 계약을 설명하며 소요 시간 측정은 아니다.

[공매 가격 비교표](../assets/odeduck-goal-flow.html)는 실험 기능의 산출물을 설명하는 가상 예시다.
물건 A의 3억 원·3.4억 원, 물건 B의 2억 원은 설명용으로 만든 값이다. 실제 조회나 결합 결과가 아니다.
단지·면적·거래 시점의 비교 조건과 자료가 부족한 항목을 함께 남긴다는 의미를 보여준다.
자동 물건 식별, 수익성 또는 이 공매 목표의 완주를 검증했다는 근거로 사용하지 않는다.
이 예시로 기존 평가 목표나 원천 검사 기록을 대체하지 않는다.
