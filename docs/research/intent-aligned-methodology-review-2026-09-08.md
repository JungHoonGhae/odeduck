# INTENT 기준 방법론 비교: 범용 탐색·분석과 사업 가설 발견

조사일: 2026-09-08. 상태: 적용 후보와 이행 방향을 제안하는 연구. 구현 승인·성능 증명·새 ADR이 아니다.
최상위 기준은 [INTENT.md](../../INTENT.md)다. 파일명은 대문자를 유지하며 이 조사에서는 수정하지 않는다.

## 1. 결정: 특정 사업이 아니라 목표를 푸는 방식을 최적화한다

사용자 의도는 키워드나 PK 없이 서로 먼 데이터와 필요한 중간 자료를 찾아 실제 목표 산출물을 얻는 것이다.
현재 구조 보존은 목표가 아니며, 구조 교체가 필요하면 검토한다. 다만 한 성공 사례에 맞춘 재작성도 피한다.
이번 대화의 추가 우선순위는 **범용 데이터 분석 능력을 유지하면서 사업 아이데이션·브레인스토밍에 먼저 도움이 되는 것**이다.
특정 업종·공공조달·대통령 관련 질문을 공통 코어의 필수 역할이나 정답 경로로 만들지 않는다.

권고: **EDA + 관측에 따른 반복 탐색 + 중간 개념을 통한 가설 발견 + 가벼운 의미/원천 매핑 계약**.
온톨로지는 배제하지 않는다. 이전의 “그래프 DB보다 답변 경로가 먼저”라는 판단을 유지하되,
재사용 가능한 의미 모델까지 미루지는 않는다. 저장 기술과 의미 모델은 서로 다른 결정이다.
구현 범위는 기존 데이터 취득·인증 보호를 재사용하면서, join 중심 목표 실행을 결과 유형 중심으로 재설계하는 안을 우선 비교한다.

| INTENT의 요구 | 이번 방법론 적용 | 완료의 증거 |
| --- | --- | --- |
| 키워드를 몰라도 시작 | 자연어 목표와 필요한 관측 제안, 어휘·컬럼 수준 후보 검색 | 숨겨둔 도메인/제공기관에서 PK 힌트 없는 탐색 |
| 의미적으로 먼 데이터 연결 | 주제 유사성 외에 관측 대상·단위·시간·공간·식별자·중간 대응표 탐색 | 서로 다른 원천의 근거 있는 결합 또는 분석 결과 |
| 첫 후보 고정 없이 대안 탐색 | 읽은 근거와 실패 유형에 따라 다음 질의 수정 | 실패 후 다른 원천/매핑으로 복구한 실행 기록 |
| 최종 산출물과 근거 | 단일 기록 답변·표·분석·가설을 구별하고 근거 위치 제공 | 원천으로 검토 가능한 결과와 남은 미확인 부분 |
| 안전한 중단과 유용한 성공 | 동명이인·시점·중복·coverage 방어 + 양성 완료 테스트 | 오탐뿐 아니라 답할 수 있는 질문의 완료율도 측정 |
| CLI/MCP 공통 기준 | 같은 의미 계약과 실행 module 사용 | 두 interface의 행동·오류·근거 동등성 검사 |

## 2. 방법론 비교: 무엇을 취하고 무엇을 도입하지 않는가

아래 적용 판단은 연구에 대한 프로젝트별 추론이다. 논문 성능을 오데덕 성능으로 옮겨 적지 않는다.
온톨로지 표준의 조항별 세부 근거는 [1차 자료 부록](ontology-methods-primary-sources-2026-09-08.md)에 둔다.

| --- | --- | --- |
| 질문 중심 온톨로지 개발 — [Ontology Development 101 §3](https://protege.stanford.edu/publications/ontology_development/ontology101-noy-mcguinness.html) | 답해야 할 질문과 재사용·유지관리 범위를 먼저 고정 | 여러 질문 유형에서 필요한 최소 개념만 정의. 전 세계 클래스부터 설계하지 않는다. 질문·매핑을 검토할 사람이 필요하다. |

| 통제 어휘 — [SKOS §8·10](https://www.w3.org/TR/skos-reference/#mapping) | 다른 표기·상하위·관련 개념을 검색에 활용 | 정의·제외 범위가 있는 작은 개념 사전. `exactMatch`는 개념 대응이며 오데덕의 exact 식별 등급이 아니다. 임의 동의어·무제한 확장 금지. |

| 제약 검증 — [SHACL §3](https://www.w3.org/TR/shacl/#validation) | 명시적 shape에 대한 위반과 근거 위치 보고 | Go validator의 규칙·버전·오류 근거를 일관되게 관리. 실제 RDF 교환이 필요할 때 SHACL runtime 평가. 구조 통과가 실제 동일성이나 참을 뜻하지 않는다. |
| 시맨틱 분석 계층 — [dbt semantic models](https://docs.getdbt.com/docs/build/semantic-models), [QUDT QuantityKind](https://www.qudt.org/doc/2026/01/DOC_SCHEMA-QUDT.html) | entity key·시간 차원·집계 의미, 수량 종류와 단위 구별 | 숫자 변환에 더해 grain·단위·분모·집계 규칙을 원천 근거에 묶는다. | 가상 지식 그래프 / OBDA — [Ontop concepts](https://ontop-vkg.org/guide/concepts.html), [R2RML §1–2](https://www.w3.org/TR/r2rml/) | 의미 질의를 매핑을 통해 원천 SQL 질의로 재작성 | 의미 모델과 물리 저장을 분리하는 설계 원칙은 유용하다. 현재 포털 API/CSV를 Ontop이 자동 통합하지는 않는다. 안정적 SQL 저장·반복 질의 수요가 생기면 핵심 실행 교체 후보. |
| OWL 추론·GraphRAG — [OWL Primer](https://www.w3.org/TR/owl2-primer/), [GraphRAG](https://arxiv.org/abs/2404.16130v2) | 분류/논리 함의 또는 수집 문서의 전역 종합 | 서로 다른 문제다. OWL 키는 DB 중복 거부가 아니며 논리적 동일성을 함의할 수 있다. GraphRAG도 현실 식별 검증의 대체재가 아니다. 반복 함의 질의·문서 전역 질문이 필요할 때 비교한다. |

검토 결과, 가장 가까운 조합은 “온톨로지 하나로 모든 추론”이 아니라 **검색용 개념 + 원천 의미 매핑 + 실행 제약 + 분석/가설 생성**이다.
각 부분을 별도 서버나 독립 프레임워크로 만들 필요는 없다. 후보 검색 그래프의 점수를 사실 그래프의 승인으로 전달하지 않는다.

## 3. 현재 코드에 없는 의미 계약을 어디에 둘 것인가

현재 `internal/catalog/search.go`는 하이브리드 검색 정책을, `goalwork/column_profile.go`는 값 없는 형태 통계를 제공한다.
`source_declaration.go`는 제공자 선언을 보존하고, `scope_vocabulary.go`는 공식 시도 표기를 버전·해시와 함께 비교한다.
`measure.go`의 Unit은 검증된 단위가 아니라 선언된 해석이며, 장부의 Namespace/Grain 역시 그것만으로 실세계 의미의 증명이 되지 않는다.
따라서 작은 사전은 이미 일부 있지만, **검색과 실행이 공유하는 검토된 원천 의미 매핑**은 별도 설계가 필요하다.

최소 관리 대상은 세 가지다. 새로운 플랫폼이 아니라 기존 원천/근거 ID를 참조하는 관리 데이터로 시작한다.

1. 개념 정의: 안정 ID, 뜻·제외 범위, 대체 표기, 검색 확장에 허용할 관계.
2. 원천 매핑: PK + 제공형 + operation/asset/필드 경로 → 개념·역할·grain·단위·기간·식별 namespace와 공식 근거.
3. 적용 조건: 필요한 필드/버전/범위, 허용 변환·연결 방식, 검토 상태, 실패·미확인 이유, 담당자와 대체 revision.

원천 매핑은 **질문별 정답 recipe가 아니다.** “이 CSV의 증정일은 어떤 사건 시점인가”는 여러 질문에 재사용할 수 있다.
“대통령 질문이면 이 PK를 읽고 이 답을 출력하라”는 평가 누출이다. 새 원천을 볼 때 LLM은 매핑 후보를 제안할 수 있지만
자기 제안만으로 검토 완료시키지 않는다. 모르는 개념은 원문에 묶인 후보로 남겨 탐색하고, 기존 사전에 없다는 이유로 버리지 않는다.

### 실제 검사한 원천은 회귀 사례로만 사용

이번 조사에서 `go run ./cmd/odeduck inspect 15132113 --delivery file --observe --format json`이 종료 0이었다.
공식 FILE: `250224_대통령 선물 및 행정박물.csv`, 452,875 bytes,
SHA-256 `3f3c25da24d99b5006f661420e9b8512088dcae9d65eabca3b5df555360cdd93`.
관측된 컬럼은 `번호`, `대통령`, `선물`, `증정인`, `증정국가`, `증정일`; schema 관찰 표본은 5행이다.
제공자 metadata의 4,071행·1953–2022년 선언을 이번 전체 행·날짜 검증으로 간주하지 않는다.

| 관측 컬럼 | 의미 매핑 제안 | 아직 확인하지 않은 것 |
| --- | --- | --- |
| 번호 | 이 원천의 record 식별 후보 | 파일 갱신 후 안정성·유일성. 전역 인물/선물 ID로 쓰지 않는다. |
| 대통령 / 증정인 | 수령인 표기 / 증정 주체 표기 | 같은 인물·기관을 가리키는 공식 ID, 각 행의 주체 유형 |
| 선물 | 증정 대상의 명칭 | 같은 이름 물품의 동일성·분류·실물 개수 |
| 증정국가 | 원천이 기록한 국가 표기 | 출생국·국적·제작국으로 바꿔 해석할 근거 |
| 증정일 | 증정 사건의 시점 후보 | 실제 값의 형식·불확실한 날짜·사건 의미의 일관성 |

이 매핑 표는 제안이며 구현하거나 자동 승인하지 않았다. 대통령/선물 클래스를 범용 엔진 필수 타입으로 넣지 않는다.
[직전 live 감사](graph-engineering-audit-2026-09-08.md)의 12단계 실패는 별도 회귀 증거이며 이번에 solve를 재실행하지 않았다.

## 4. 장기 구조: 무엇을 보존하고 무엇을 바꿀 것인가

목표 구조는 하나의 배포 단위 안에서 다음 책임을 나눈 **modular monolith**다. 아래는 논리적 module이며 새 package/서버 수를 뜻하지 않는다.

| Module | 작은 interface가 제공할 것 | 바꿔도 보존할 계약 |
| --- | --- | --- |
| 원천 취득 | catalogued source의 검사·읽기·가능 행동 | data.go.kr 범위, typed Adapter, 키 비노출, 제한·취소·원문 위치 |
| 의미·발견 | 목적에 맞는 개념/필드/원천 후보와 적용 가능한 매핑 | 검색 점수와 승인 분리, 버전/namespace/시간·단위 근거 |
| 목표 실행 | 요구 결과에 필요한 읽기·변환·연결·분석 실행 | typed 연산, 예산·lineage·중복/시점 검증, CLI/MCP 동등성 |
| 근거·검토 | 관측 사실·계산 결과·해석 가설과 검토/정정 상태 | append-only 판정, source revision, 재현 가능한 근거, 미확인/실패 구별 |

사용자 목표는 보존하되 초기 모델의 해석까지 영구 정답으로 고정하지 않는다. 근거로 해석을 수정하면 revision과 이유를 남긴다.
전체→표본 축소처럼 목표가 바뀌는 선택은 사용자에게 묻고, 키 이름이나 대응 원천 발견은 자율 진행한다.
출력은 단일 원문 근거·관계형 결과·탐색 분석·가설을 구분한다. 테이블 join은 선택 가능한 연산이지 모든 목표의 완료 조건이 아니다.
계획기는 도구 전체 설명을 매번 읽는 대신 현재 원천/상태에서 가능한 행동을 받는다. 상세 실행 검사는 항상 실행 module이 소유한다.

관계 모델은 기존 네 층을 유지한다: Source(제공 계약), Record(원문 버전/위치), Entity(근거가 있는 대상 식별),
Claim/Event(특정 출처·시점의 주장/사건). 주제 관련성·동일 대상·실제 사건 관계를 같은 edge로 합치지 않는다.
exact는 동일 발급 namespace·유효 범위, deterministic은 근거 있는 변환, probabilistic은 후보, unresolved는 미확인이다.
이 등급과 개념 사전의 대응 관계 이름은 별개의 필드다. 읽은 시간, 원천의 사건/측정 시점, 유효 기간을 구분한다.

### 세 가지 이행안 비교

| 안 | 장점 | 장기 비용 / 선택 |
| --- | --- | --- |
| 현재 구조에 예외 계속 추가 | 단일 회귀를 빨리 고칠 수 있음 | 질문별 분기·거대한 프롬프트가 늘 수 있다. 임시 회귀 수정에는 가능하지만 최종 구조로 고정하지 않는다. |
| **목표 실행 interface와 의미 계약 재설계, 취득/검증 재사용** | 범용 결과를 허용하고 반복 의미 해석을 관리 데이터로 분리 | public 계약 이행·과거 fixture 호환 비용이 있다. 현재 우선 비교안이다. |
| 전면 RDF/OWL/OBDA 또는 그래프 DB 기반 재작성 | 표준 교환·반복 의미 질의·가변 경로에 이득 가능 | 수집/인증 문제는 남고 매핑·저장·추론 운영까지 늘어난다. 외부 호환 요구나 측정된 병목이 있으면 전면 교체도 가능하나 현재 우월성 미입증. |

승인 후 이행 순서 제안: 공통 결과/근거 계약과 실패 재현 → 기존 reader를 연결한 새 경로 shadow 비교 →
단일 원천/다중 원천/분석 유형의 양성·음성 통과 → CLI/MCP 호환 Adapter 전환 → 사용되지 않는 옛 경로 폐기.
장기간 dual-write는 피한다. 과거 장부를 새 의미로 자동 재해석하거나 기존 dirty 파일을 일괄 삭제하지 않는다.
새 경로의 출력/근거 차이와 rollback 경로가 확인되기 전까지 기본 실행을 전환하지 않는다.

## 5. 사업 브레인스토밍에 유리한 활용 방식 — 범용 분석 위의 선택형 출력

핵심은 “창업 아이디어 생성기” 전용 코어가 아니라 **데이터 관측 → 설명 가능한 차이 → 가설 → 반증**이다.
수요·공급·접근성·시간 변화·업무 부담 같은 분석 관점을 선택할 수 있으나 모든 질문에 이 역할을 강제하지 않는다.
구매자가 없는 초기 탐색도 가능하다. 단, 그런 결과는 사업성이 검증된 기회가 아니라 구매자 가설을 가진 탐색 결과다.

기회 카드의 최소 내용: 관측 사실과 범위/기간/분모 → 원천 연결 근거 → 가능한 고객·문제 가설 → 기존 대안 →
수익으로 이어질 수 있다는 가정 → 반대 설명/추가 필요 데이터 → 다음 검증 또는 중단 조건.
사실·계산·사업 가설·고객 검증을 분리해 표시한다. 통계적 특이점, 의미적 거리, 데이터셋 수를 수익 점수로 합치지 않는다.
인구는 수요의 proxy일 수 있고 시설 수는 공급 능력을 직접 뜻하지 않는다. 표본에서 비어 보이는 지역을 “미개척 시장”으로 단정하지 않는다.
많은 조합을 탐색한 뒤 뽑은 패턴은 탐색 결과로 표시하며 독립 기간/지역 검증 전에는 일반화·인과를 주장하지 않는다.

이번에는 특정 사업·고객·시장·가격을 새로 선정하지 않는다. 개별 후보를 검증할 때는
[사업 하네스](../../.agents/skills/odeduck-business-harness/SKILL.md)의 무료/수작업/직접 대체재와 지불 증거 기준을 적용한다.
공공데이터는 모든 구매 의사를 담고 있지 않다. 인터뷰·고객 원장·결제 증거가 필요하면 미확인 또는 사용자 입력으로 남긴다.
data.go.kr 코어를 다중 포털 수집기로 몰래 넓히거나 고객 접촉을 자동 승인하지 않는다.

## 6. 과적합 방지: 대통령 사례 통과와 범용성은 별개

질문 유형을 기준으로 골드를 설계한다. 아래 분야 조합은 시험 제안이며 실제로 원천을 확보했다는 주장이 아니다.

| 질문 유형 / 산출물 | 시작 → 필요한 경로 | 오탐·시간 정책 |
| --- | --- | --- |
| 단일 사실 확인 / 인용 카드 | 목표 → 해당 시점의 공식 record | 인용 없는 사실 0, join 강제 0 |
| 조건 검색 / 근거 있는 목록 | 요구 조건 → 관측 필드/매핑 → 필터 | unknown과 불충족 구분, 기준일 보존 |
| 분포·집계 / 분석표 | 관측 집합 → 단위·grain·분모 → 집계 | 중복 집계 0, 표본을 모집단으로 승격 0 |
| 교차 원천 연결 / 비교표 | 서로 다른 원천 → 공식 식별/대응표 → 결합 | namespace·동명이인·분할/합병 반례의 확정 오탐 0 |
| 시간·공간 비교 / 차이와 한계 | 사건/관측 → 경계/시점 정합 → 비교 | 당시 경계·단위 확인, 직선거리를 접근 가능성으로 전용 0 |
| 가설 탐색·반증 / 다음 검증 | 관측 → 중간 연결 → 가설 → 반대 증거 | 인과·부재·지불을 추정 사실로 말하지 않음, 정정 시 과거/현재 분리 |

초기 평가 설계는 6유형 × 4분야의 최대 24개 양성 목표와 별도 hard negative/정정 세트다.
분야는 문화 기록, 지역 생활/이동, 환경·시설, 기업 활동 등으로 나누되 data.go.kr 원천 확보 가능성을 먼저 확인한다.
각 분야의 모든 유형이 실제로 답 가능한지 확인하지 못하면 시험 미확정으로 남긴다. 답하기 쉬운 목표로 몰래 교체하지 않는다.
대통령 질문은 그중 하나의 회귀이며, 조달/식품도 정답 경로가 아니라 분야 예시다.

평가 분리는 도메인·제공기관 단위다. 한 분야를 숨기는 순환 평가를 하되 숨긴 원천의 정답으로 매핑을 수정하지 않는다.
(A) 무사전 매핑 상태, (B) 새로운 원천 매핑을 검토해 제공한 적응 상태를 따로 측정한다.
B의 성과를 A의 zero-shot 일반화로 보고하지 않는다. 적응에 든 사람 시간, 새 코드/프롬프트 분기 수도 기록한다.
지원되는 형식의 새 원천은 매핑/fixture 추가만으로 확장되는지 확인한다. 미지원 형식은 reader 비용으로 따로 분류한다.

비교군: 같은 원천·모델·예산에서 baseline 검색+읽기, +반복 탐색, +의미 매핑, +컬럼/연결 색인을 한 번에 하나씩 추가한다.
반복 실행·순서 교대·캐시 기록을 하고, 발견률/답변 완료율/출처 추적률/오탐/unknown/시간·호출비용/매핑 유지비를 함께 본다.
가설 출력은 사용자 유용성·반증 가능성으로 평가하고, 실제 시장 검증 완료율과 분리한다.
0건 오탐은 시험 통과선이지 모집단 정확도 보장이 아니다. 전부 중단하는 방식도 실패다.

평가 주의 근거: [LakeBench §6.2](https://www.vldb.org/pvldb/vol17/p1925-chai.pdf)는 컬럼 유사성이 높아도 표 전체 의미가 달라
union할 수 없는 반례를 다룬다. [2025년 재평가 §5](https://aclanthology.org/2025.trl-1.7.pdf)는 단순 baseline도 강한 점수를 얻는
벤치마크 특성을 지적한다. 해외 table benchmark를 한국 공공데이터의 실세계 동일성/사업 효용 골드로 그대로 쓰지 않는다.

## 7. 지속 개선의 운영 계약

- 매핑/개념마다 검토 책임자, 원천 근거와 적용 범위, 버전, 양성·반례 fixture를 둔다. 새 조직/위원회부터 만들지 않는다.
- 표기 수정, 의미 변경, 원천 schema 변경, 행 데이터 갱신을 구분한다. 의미 변경은 새 revision/개념 ID와 의존성 재검증 대상이다.
- 단순 신규 행 추가만으로 모든 의미 매핑을 폐기하지 않는다. 반대로 field 이름이 같다는 이유로 바뀐 의미를 재사용하지 않는다.
- 원천/매핑/검증 규칙이 바뀌면 영향을 받는 결과만 stale로 표시하고 재검증한다. 역사적 판정은 supersedes와 당시 버전으로 보존한다.
- 실행 manifest에는 코드·모델·카탈로그·매핑·원천 버전과 예산·실패를 묶는다. 해시만 있고 원본 복원이 불가능하면 재현 한계를 명시한다.
- 새 live 실패는 고정 회귀 사례로, 반려된 동일시는 hard negative로 축적한다. LLM이 만든 답만으로 골드와 승인 규칙을 동시에 만들지 않는다.
- 실제 소비가 없는 개념과 중복 상태/설명은 의존성을 확인해 축소한다. 취득 제한·인증키 보호·lineage 검증은 복잡하다는 이유로 없애지 않는다.
- 저장/실행 교체는 baseline 대비 완료율·운영 비용·변경 범위·정정 재현에서 이득이 있을 때 결정한다. 현재 구현 유지도 검증 대상이다.

## 8. Andrej Karpathy 참조로 보완한 설계

사용자의 추가 요청에 따라 Karpathy 본인의 자료를 확인했다. `INTENT.md`가 목적이며 아래 자료는 설계 참고다.
Software 2.0과 작은 구현의 실제 범위는 [별도 원문 검토](karpathy-software-principles-2026-09-08.md)에 둔다.

### LLM Wiki: 검색 결과가 아니라 재사용할 지식을 남긴다

[Karpathy의 LLM Wiki 원문](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)은
불변 원천, LLM이 관리하는 연결된 wiki, 유지 규칙을 분리한다. 수집·질의·점검을 반복하며 모순과
새 질문도 남기는 아이디어다. 약 100개 원천 규모의 개인 사용 설명이지 공공데이터 전체의 검증 결과가 아니다.
원문의 유지비가 거의 없다는 주장이나 wiki 일관성에 대한 기대를 오데덕의 보장으로 옮기지 않는다.

오데덕 적용 제안은 **근거에 묶인 재사용 지식**이다. 원천 필드 의미, 유효한 대응표, 기각한 연결과 이유,
분석의 한계·미해결 질문을 다음 목표에서 검색한다. 기존 `connectionledger`의 판정과
`goalwork`의 실행 중 이력을 대체하지 않고 해당 원천/판정을 참조하는 파생 읽기 모델로 설계한다.
현재 확인한 `internal/agentplan/goal.go`의 요청·실패 이력 재사용만으로 이 교차 세션 지식 재사용이 구현됐다고 보지 않는다.

파생 요약에는 원천·판정 ID, 적용 범위, 버전, 검토 상태를 붙인다. 요약이 다른 요약을 인용한 횟수를
독립 근거 수로 세지 않는다. 원천 변경 시 관련 요약은 stale로 표시하고 재확인한다.
원문 접근권한·민감정보 정책은 파생물에도 전파한다. 개인 세션 자료를 공용 카탈로그로 승격하지 않는다.
LLM은 해석과 매핑을 제안하지만 검증 장부를 임의 수정하거나 자기 서술을 사실로 승인하지 않는다.

Markdown은 사람이 검토할 출력 후보이고 typed record가 실행 판단을 맡는다. 같은 정보를 양쪽에서
독립 수정하지 않는다. 원천/장부를 기준으로 다시 만들 수 있는 projection이면 충분하며, 처음부터 별도
wiki 제품·Obsidian 의존성·그래프 DB를 추가할 이유는 없다. 검색은 신규 원천을 찾고, 축적 지식은 이전
발견을 재사용하므로 둘을 비교해 하나를 없애는 문제도 아니다.

### autoresearch: 아키텍처도 제한된 실험으로 개선한다

[공식 README](https://github.com/karpathy/autoresearch)와
[program.md](https://github.com/karpathy/autoresearch/blob/master/program.md)는 수정 대상과 고정 평가를 분리하고,
기준 실행 후 일정한 학습 예산에서 결과를 비교한다. 동등한 결과라면 단순한 구현을 선호하는 기준도 명시한다.
이 프로젝트는 LLM 학습 실험이다. 사업 가설의 유용성이 단일 자동 점수로 판정된다는 근거는 아니다.

우리의 적용 판단: **실험자는 탐색 전략을 바꾸고, INTENT·평가 정답·승인 규칙은 같은 실험 중 바꾸지 않는다.**
비교 대상은 재검색 전략, 문맥 선택, 의미 매핑, 연결 후보 색인이다. 동일한 모델·원천 snapshot·호출/시간
예산을 사용하고 변동성도 기록한다. 잘못된 동일시·근거 누락은 별도 탈락 조건으로 두고, 이를 통과한 안의
목표 완료율·유용성·검토 시간·운영비를 비교한다. 앞 절의 숨긴 도메인 평가와 매핑 유지비까지 포함한다.
여러 실험에 반복 노출된 평가셋은 개발셋으로 보고 최종 검증셋을 별도로 유지한다.

개선이 없는 복잡도는 추가하지 않으며, 같은 결과를 더 단순하게 얻는 변경도 개선으로 인정한다.
학습용 5분·단일 지표를 그대로 복사하지 않는다. 무제한 루프·권한 해제·공유 dirty worktree의 reset도 이식하지 않는다.
실제 실험 실행은 별도 범위·예산·격리 작업공간 합의 후 진행하며 이번 조사에서는 실행하지 않았다.

### 이전 권고에서 달라진 우선순위

경량 온톨로지를 독립적인 큰 선행 구축으로 두지 않고, **목표 실행 중 얻은 원천 의미와 연결 근거를 재사용하는
최소 계약**으로 시작한다. 그 계약이 다음 질문의 완료율을 높이는지 측정한다.
제품의 탐색→검증→분석 반복과 개발의 변경→평가→채택 반복은 다른 과정이며, 제품이 실행 도중 스스로
코드나 승인 규칙을 바꾸는 자기수정 구조를 제안하지 않는다.
사업 브레인스토밍은 이 기반에서 관측 사실·반대 설명·고객 가설을 축적하는 우선 활용처로 유지한다.

## 9. 이번 조사에서 확인한 것과 남은 것

1차 규격의 관련 조항, Aurum의 구성/후보 관계, IRCoT의 검색/reader 절차, LBD의 가설과 증명 구분,
NIST EDA 정의, table benchmark의 반례·재평가, 현 코드와 공개 FILE schema를 확인했다.
온톨로지 runtime·비교군·held-out 평가·새 실행 구조는 구현/실행하지 않았다. 도입 효과·개발 기간·운영비는 아직 미측정이다.
이 문서는 여러 개의 새 개발 목표를 시작하거나 이전 미완료 계획을 완료 처리하지 않는다. 구현 시 기존 ADR과 이행 계약을 함께 검토해야 한다.
제품 코드, INTENT.md, CONTEXT.md, 기존 dirty 변경, 로그인/인증키/신청 상태를 변경하지 않았다.
결론은 **INTENT를 위한 범용 탐색·분석의 구조 개선을 검증하되, 첫 효용 평가는 사업 가설 발견에 무게를 둔다**이다.
