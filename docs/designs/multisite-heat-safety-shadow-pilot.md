## Problem Statement

20개 이상의 야외 작업 현장을 책임지는 본사 안전보건 책임자는 무료 기상 알림, 현장 온습도계,
전화·단체대화방, 엑셀·점검표를 오가며 폭염 대응을 지시하고 이행 여부를 취합하는 것으로 추정된다.
본사는 위험 현장보다 **측정·조치·확인이 끝나지 않은 현장**을 제때 알아야 하지만, 현재 방식의 실제
소요시간·누락률·비용은 아직 관찰하지 못했다.

사업 기회는 날씨 알림이나 법적 준수 판정이 아니다. `위험 탐지 → 현장 측정 → 조치 판단 → 사람의
승인·확인 → 미응답 에스컬레이션 → 재현 가능한 증빙`을 닫는 예외관리 서비스다. odeduck은 기상청
원천의 계약·호출·출처를 보존하는 내부 데이터 계층이자, 유료 검증 성공 후 공개할 대표 활용 사례다.

## Demand Evidence

- 직접 수요 증거는 아직 없다. 고객 인터뷰, 실제 업무기록, LOI, 유료 파일럿, 관찰된 시간 비용이 모두
  없는 pre-product 단계다.
- 2025년 강화된 폭염작업 규칙과 2026년 정부 감독은 문제의 긴급성을 뒷받침하지만 지불의사를 증명하지
  않는다. 기상청 알림과 고용노동부 점검표·기술지원도 무료다.
- odeduck 카탈로그에서 기상청 단기예보 `15084084`, 기상특보 `15000415`, 과거 폭염
  `15075950`, 산업재해 현황 `15002274`의 제공성과 계약을 확인했다. 데이터 실행 가능성은 확인됐지만
  data.go.kr 로그인·활용신청 후 실제 호출 품질은 검증 전이다.
- 공식 근거, 후보 비교, 원천 링크는 `docs/research/best-business-opportunity-2026-09.md`에 있다.

## Status Quo

현재 검증할 업무 가설은 다음과 같다.

1. 본사 담당자가 기상청 알림이나 자체 예보를 보고 위험 현장을 고른다.
2. 현장관리자가 작업 장소에서 온도·습도 또는 체감온도를 측정한다.
3. 본사가 전화나 단체대화방으로 휴식·작업조정 지시를 보낸다.
4. 현장이 사진·메시지·점검표로 조치 사실을 회신한다.
5. 본사 담당자가 엑셀로 취합하고 미회신 현장을 다시 추적한다.

인터뷰에서는 “필요한가”를 묻지 않는다. 최근 폭염일의 실제 대화방, 점검표, 측정 기록을 화면으로
보면서 각 단계의 담당자·소요시간·누락·재작업을 재구성한다. 자료를 볼 수 없는 인터뷰는 정성적 관심
신호로만 분류한다.

## Target User & Narrowest Wedge

- **구매자 가설:** 20~50개 야외 작업 현장을 책임지는 중견 건설 원청의 본사 안전보건 책임자.
- **파일럿 표본:** 조직당 10개 현장, 두 조직, 총 20개 현장. 구매자 조직의 전체 현장 수와 파일럿에
  포함하는 표본 수를 구분한다.
- **현장 사용자:** 현장 안전관리자 또는 관리감독자. 작업자는 별도 계정 없이 고객의 기존 확인 절차를
  사용하며 개인 건강정보는 받지 않는다.
- **최초 위험:** 폭염 하나. 한파·호우·대기질은 유료 갱신 뒤에만 검토한다.
- **가장 작은 유료 결과물:** 매일의 미측정·미판단·미확인 예외 목록과 원천·측정·승인·확인 시각이
  묶인 CSV 증빙 한 형식. PDF는 실제 구매자가 요구할 때만 추가한다.

## Constraints

- 공공 5km 예보는 측정 우선순위를 정할 뿐 법정 체감온도 측정이나 준수 판정을 대신하지 않는다.
- 고객 법무·노무 검수를 받은 조치 문구와 고객의 최종 승인을 보존하며 “법적 준수 보장”을 판매하지
  않는다.
- 고객의 기존 안전 절차가 유일한 권위 있는 지시·긴급대응 경로다. 섀도 운영은 이를 대체하거나 늦추지
  않는다.
- 개인 건강정보, 임상 예측, 작업자 프로파일, 자동 징계 기능은 범위 밖이다.
- 범용 규칙 엔진, 네이티브 앱, AI 권고, 급여·HR 연동, 센서 제조사별 연동, 멀티테넌트 플랫폼은
  유료 갱신 전에는 만들지 않는다.
- office-hours 단계에서는 제품 코드를 구현하지 않는다. 고객 행동 게이트 통과 뒤에만 구현한다.

## Premises

1. 무료 알림보다 본사의 미조치·미확인 예외를 닫는 것이 유료 가치다.
2. 본사 안전보건 책임자는 구매자 **가설**이며 실제 예산권자와 결재 경로를 확인해야 한다.
3. 공공데이터는 위험 우선순위와 원천 증빙을 제공하고, 현장 측정값과 고객의 사람이 실제 조치를
   통제한다.
4. odeduck은 고객 화면의 중심이 아니라 데이터 provenance 계층이다. 독립 제품이 이기지 못하면
   odeduck 사례라는 이유로 유지하지 않는다.
5. 구매 신호는 설문이나 무상 LOI가 아니라 실제 자료 접근, 담당자 시간, 임원 스폰서, 조달 착수,
   최종 결제로 단계적으로 측정한다.

## Approaches Considered

- **Approach A — 컨시어지 섀도 검증 후 단일 폐쇄루프 구현 (선택):** 실제 업무와 구매 행동을 먼저
  검증한 뒤 반복 단계만 자동화한다.
- **Approach B — 48시간 파일럿 앱 선구현 (기각):** 데모는 빠르지만 관찰하지 않은 워크플로를 코드로
  고정하고 호감을 수요로 오인할 위험이 크다.
- **Approach C — 안전보건대행기관 채널 우선 (보류):** 여러 현장 접근은 쉽지만 간접 구매자,
  파트너 의존성, 멀티테넌시 복잡도가 생긴다. 직접 고객의 유료 갱신 뒤 유통 채널로 재평가한다.

## Recommended Approach

### Stage 0 — 발견 인터뷰, 접촉 7일·완료 21일

1. 중견 건설 원청 30곳의 본사 안전보건 책임자를 특정한다. 최소 5건은 산업안전 전문가, 협회, 기존
   지인을 통한 따뜻한 소개로 확보하고 나머지는 직접 연락한다.
2. 첫 7일에는 30곳 모두에 연락하고 인터뷰 일정 10건을 잡는다. 인터뷰·후속 자료 walkthrough는
   최대 21일 안에 완료하고, 최근 폭염일 실제 기록 walkthrough 3건과 섀도 검증 후보 2곳을 목표로
   한다.
3. 민감 자료는 화면 공유만 받고 저장하지 않는다. 저장이 필요하면 고객이 현장명·작업자명을 가린 사본,
   NDA, 사용 목적과 삭제일에 동의한 경우에만 받는다.
4. 산업안전·노무 전문가에게 측정·조치 의사결정표와 파일럿 책임 경계를 검수받는다.
5. 사용자가 data.go.kr에 로그인한 뒤 odeduck으로 `15084084`, `15000415`를 활용신청하고 표본
   호출한다.

7일 안에 인터뷰 일정이 5건 미만이면 물류·시설관리 연락을 별도 discovery cohort로 시작한다. 건설과
다른 업종의 인터뷰·지표·구매 결과는 합산하지 않으며 Gate 1은 같은 업종의 독립 조직 두 곳으로만
통과한다. 21일 안에 실제 기록 walkthrough 3건이나 후보 2곳을 확보하지 못하면 섀도 검증으로 가지
않고 구매자, 업종 또는 문제를 다시 정한다.

Stage 1 진입 전에는 두 KMA operation의 정상·빈 응답 표본 호출, 발표시각·유효시각 의미, 서비스키
갱신 절차, 상업적 저장·고객 증빙 사용조건을 확인해 기록한다. 하나라도 확인하지 못하면 공공데이터
연결 없이 고객 기존 기록만으로 workflow discovery를 계속하고 위험 후보 성능은 검증하지 않는다.

### Stage 1 — 무상 사후비교형 섀도 검증, 최대 30일

두 후보 조직에서 각 10개 현장을 표본으로 삼는다. 고객은 기존 채널로 위험 후보 선정, 측정 요청,
조치 판단과 지시를 모두 먼저 수행한다. 컨시어지 운영자는 그 결과를 전사하고, odeduck/KMA가 독립적으로
만든 위험 후보와 **업무 종료 뒤** 비교한다. 섀도 결과는 같은 날의 실제 요청·판단·에스컬레이션을
발생시키지 않는다.

```text
고객 기존 절차 → 측정 → 조치 판단 → 수신 확인 → 조치 완료
       ↓                                      ↓
  컨시어지 수기 전사 → append-only 비교표 ← odeduck/KMA 사후 후보
```

Stage 1에는 새 서버, 공개 폼, 입력 링크 또는 제품 코드를 만들지 않는다. 고객이 승인한 고객 소유
SharePoint·Google Workspace·사내 파일 저장소 안에서 가명화한 현장 ID와 이벤트 표를 관리한다.
고객 소유 도구에서 목적 제한·접근 로그·삭제일을 보장하지 못하면 섀도 검증을 시작하지 않는다.

섀도 검증은 시작 동의서가 서명되고 첫날 현장 roster·작업계획·기준선 기록을 받은 시점부터 기산한다.
다음 중 먼저 도달할 때 종료한다.

- 30 calendar days
- 조직별 최소 10개, 전체 최소 30개의 `closed loop`와 최소 3개의 적격 위험일

30일 동안 적격 위험일이 3일 미만이면 과거 폭염 자료 재생으로 화면·증빙 흐름만 검증한다. 재생 결과는
실시간 탐지 성능이나 구매 검증을 대신하지 않으며 Gate 1의 운영 품질 항목은 “미검증”으로 남긴다.

### 용어와 판정 계약

| 용어 | 운영 정의 | 증거와 판정자 |
| --- | --- | --- |
| 적격 작업블록 | 파일럿 roster의 현장에서 시간·장소가 명시된 야외 작업 | 고객 작업계획, 본사 책임자 확정 |
| 위험 후보 | KMA 예보·특보가 고객이 사전 승인한 **측정 요청 규칙**에 해당 | SourceSnapshot, 본사 책임자 승인 |
| 현장 기준 초과 | 고객이 승인한 방식으로 측정한 값이 고객의 검수된 기준에 해당 | FieldMeasurement, 현장관리자 입력·본사 확인 |
| 수신 확인 | 고객의 조치 지시를 현장 책임자가 받았다고 확인 | 기존 채널 시각, 현장관리자 확인 |
| 조치 완료 | 휴식·작업변경 등 고객이 정한 조치가 실제 끝났다고 책임자가 확인 | 고객 승인 증거, 본사 책임자 확인 |
| closed loop | `closed_no_action`, `closed_action_complete`, `closed_cancelled` 중 하나로 끝난 루프. `fallback`은 제외 | 이벤트 타임라인, 본사 책임자 승인 |
| 명시적 스폰서 | 현장·담당자 제공과 구매 검토를 서면으로 승인한 임원 또는 예산권자 | 이메일·회의록·서명 문서 |
| 조달 착수 | 가격·범위가 전달되고 예산 담당자와 벤더 등록·발주 단계 및 예정일이 기록됨 | 구매 담당자 확인 |
| 유료 배포 | 독립 조직의 자금이 실제 입금되거나 취소 불가 발주서가 발행됨 | 입금·발주 증빙 |

### 운영 상태와 책임

상태는 `eligible → measurement_requested → measurement_valid → decision_recorded`까지 공통이다.
이후 `decision_no_action → closed_no_action`, 또는 `decision_action_required → order_received →
action_completed → closed_action_complete`로 분기한다. 고객이 정당한 사유로 취소하면 `cancelled →
closed_cancelled`, 기존 절차로 복귀하면 `fallback`으로 끝난다. `fallback`은 closed loop로 계산하지
않는다. 예외 상태는 `overdue`, `needs_correction`이며 모든 변경은 이전 이벤트를 덮어쓰지 않고 정정
사유와 시각을 새 이벤트로 추가한다.

| 단계 | 실행(R) | 최종책임(A) | 협의/통보 |
| --- | --- | --- | --- |
| 현장 roster·작업계획 확정 | 본사 담당자 | 본사 안전보건 책임자 | 현장관리자 |
| 업무 종료 뒤 KMA 위험 후보 생성 | 컨시어지 운영자 | 본사 안전보건 책임자 | 산업안전 전문가 |
| 측정 요청 승인·기한 설정 | 본사 담당자 | 본사 안전보건 책임자 | 컨시어지 운영자 |
| 현장 측정·오류 정정 | 현장관리자 | 본사 안전보건 책임자 | 컨시어지 운영자 |
| 조치 필요 여부와 내용 판단 | 고객 현장/본사 담당자 | 본사 안전보건 책임자 | 산업안전 전문가 |
| 지시 수신·조치 완료의 기존 기록 확인 | 현장관리자 | 본사 안전보건 책임자 | 컨시어지 운영자 |
| 사고·긴급대응 | 고객 기존 안전조직 | 고객 | 컨시어지 운영자는 즉시 통보 후 중단 |
| 증빙 내보내기·삭제 승인 | 컨시어지 운영자 | 본사 안전보건 책임자 | 고객 보안담당자 |

요청·측정·수신 확인·조치 완료 기한과 단계별 연락 대상은 고객의 기존 규정을 그대로 기록한다. 섀도
운영자는 이를 변경하거나 새 연락을 보내지 않는다. 야간·휴일, 연락 불가, 중복 제출, 비현실적 값,
좌표 불일치는 고객이 기존 방식으로 처리한 결과를 `fallback` 또는 `needs_correction`으로 전사한다.

컨시어지 운영자는 고객 원본 이벤트 뒤 30분 안에 가명 ID, 원본 시스템, 원본 timestamp, 이벤트 종류를
비교표에 전사한다. 원본 메시지·파일은 복사하지 않고 고객 시스템의 참조 ID만 기록한다. 본사 담당자는
매일 종료 시 전사본을 원본과 대조해 승인하며, 승인 전 데이터는 성과지표에 포함하지 않는다.

### 섀도 운영 용량

- 한 컨시어지 운영자가 하루 최대 40개 루프를 다룬다. 계획 혼합은 정상 33건×5분 + 예외 7건×15분 =
  270분이다.
- 예외가 7건을 넘거나 예상 작업이 270분을 넘으면 새 루프 전사를 받지 않고, 고객이 미리 승인한 표본
  안에서 먼저 발생한 루프만 처리한다. 처리하지 못한 표본 루프는 `capacity_excluded`로 별도 보고하며
  coverage가 좋아 보이도록 분모에서 몰래 제거하지 않는다.
- 예상치가 실제 중앙값과 50% 이상 다르면 처리용량과 가격 가설을 다시 계산한다.

### 안전·보안 선행조건

실제 고객 자료를 다루기 전에 다음을 모두 확인한다.

- 고객이 유일한 안전 의사결정자이며 기존 긴급대응 절차가 항상 우선한다는 파일럿 동의서
- 고객이 승인한 측정·조치 문구, 연락망, 야간·휴일 fallback, 사고 발생 시 즉시 중단 절차
- 고객 소유 저장소의 조직별 공간, TLS 전송, 저장 암호화, 최소권한 운영자 계정과 접근 로그
- 고객 소유 저장소의 백업·복구 정책 확인, 파일럿 종료 90일 뒤 비교표 삭제 확인
- 권한 오부여, 조직 간 노출, 무단 접근 의심 시 접근 차단·고객 통보·원인 확인 전 운영 중단
- 작업자 개인 건강정보와 주민번호를 입력·첨부하지 않는 입력 검증 및 운영자 교육

실제 안전사고, 잘못된 고객 명의 지시, 조직 간 데이터 노출, 단위·시각·좌표·현장 ID가 맞지 않는 데이터
무결성 이상이 발생하면 섀도 운영을 중단한다. 정상적인 예보와 현장 측정 차이는 중단 사유가 아니라
false-priority와 audited exceedance 분석에 포함한다. 재개는 고객 책임자와 전문가의 서면 승인을 받는다.

### 지표 계약

| 지표 | 계산 | 최소 표본·판정 |
| --- | --- | --- |
| 기존 요청 coverage | 고객 기존 절차의 측정 요청 수 / 고객이 사후 확정한 위험 후보 수 | 현재 고통의 기준선; 합격선으로 사용하지 않음 |
| 기존 측정 completion | 유효 측정 수 / 고객 측정 요청 수 | 현재 고통의 기준선; 취소·capacity 제외 별도 보고 |
| 기존 판단 coverage | 고객 판단이 기록된 수 / 유효 측정 수 | 현재 고통의 기준선 |
| 기존 수신 completion | 기한 내 `order_received` / 조치 지시 수 | 현재 고통의 기준선 |
| 기존 완료 completion | 기한 내 `action_completed` / 완료 확인이 필요한 조치 수 | 현재 고통의 기준선 |
| shadow capture | 본사가 확인한 원본 이벤트 중 비교표에 정확히 전사된 수 / 확인한 원본 이벤트 수 | Gate 1 목표 95% 이상, 핵심 이벤트 누락 0건 |
| audited exceedance miss | 고객 기존 기록과 비위험 후보 20% 표본감사에서 확인한 현장 기준 초과 중 고객 판단이 없었던 수 | 요청 전 누락 포함, 목표 0건; 전문가·본사 공동 판정 |
| false-priority | 현장 기준 초과가 아니었던 KMA 위험 후보 / 유효 측정이 있는 KMA 위험 후보 | 첫 파일럿은 기준선 탐색만 하며 합격선으로 사용하지 않음 |
| 처리시간 변화 | 같은 종류의 기존 루프와 Operating Gate 뒤 유료 보조 루프의 본사 투입분 paired median 비교 | 최소 30쌍; 30% 감소 목표 |
| provenance 재현 | 종료 유형별 필수 이벤트 집합이 모두 있는 closed loop / closed loop | 목표 100% |

기준선은 조직별 최근 적격 위험일 최대 3일의 기록에서 루프 15개 이상을 뽑아 본사 투입시간을
재구성한다. 처리시간은 조직, 현장 유형, 위험 수준 구간, 조치 필요 여부가 같은 기존 루프와 Operating
Gate 뒤 유료 보조 루프끼리 매칭한다. 매칭되지 않은 건과 기억에 의존한 시간은 분포만 보고 paired
comparison에서 제외한다.

`audited exceedance miss`는 (a) 적격 작업블록의 80% 이상을 덮는 기존 상시 측정 기록이 있거나,
(b) 고객과 전문가가 승인한 비위험 후보 20% 독립 측정을 추가한 경우에만 계산한다. 둘 다 없으면
`unobservable`로 표시한다. 이때 Operating Gate는 자동 위험 우선순위·측정 요청을 허용하지 않고,
고객이 이미 만든 측정·판단 기록의 사후 예외관리만 허용한다.

종료 유형별 핵심 이벤트는 다음과 같다. `SourceSnapshot`은 KMA 연결을 사용한 모든 유형에 공통이다.

- `closed_no_action`: WorkBlock, measurement_requested, measurement_valid, decision_no_action
- `closed_action_complete`: WorkBlock, measurement_requested, measurement_valid,
  decision_action_required, order_received, action_completed
- `closed_cancelled`: WorkBlock, cancelled reason, customer approver; 취소 시점 뒤 단계는 요구하지 않음

`provenance 재현`은 각 종료 유형에 해당하는 필수 이벤트 집합이 모두 있을 때만 성공이다. Gate 1의
“핵심 이벤트 누락 0건”도 이 목록을 그대로 사용한다.

| 상태 | shadow capture 분모 | closed loop 수 | completion 분모 | paired time | provenance |
| --- | --- | --- | --- | --- | --- |
| `capacity_excluded` | 포함, 미전사면 실패 | 제외 | 제외하되 건수 공개 | 제외 | 제외 |
| `fallback` | 원본이 있으면 포함 | 제외 | 제외하되 사유 공개 | 제외 | 제외 |
| `needs_correction` | 포함 | 해결 전 제외 | 미완료로 포함 | 해결 뒤만 포함 | 해결 뒤 판정 |
| `closed_cancelled` | 포함 | 유효 사유가 있으면 포함 | 취소 뒤 단계는 제외 | 제외 | 취소 유형 필수 이벤트로 판정 |

### Gate 1 — 최소 제품을 만들 조건

두 조직이 각각 10개 현장과 운영 담당자를 제공하고 다음을 모두 충족해야 한다.

- 최근 실제 기록 walkthrough와 기준선 수집 완료
- 임원·예산 스폰서의 서면 확인
- 섀도 검증에서 조직별 10개 이상 `closed loop` 제공. `fallback`, `capacity_excluded`는 포함하지 않음
- 가격·범위를 받은 구매 담당자가 벤더 등록 또는 발주 절차와 예정일 확인
- 보안·책임 경계에 대한 고객 승인
- shadow capture 95% 이상, 핵심 이벤트 누락 0건, provenance 재현 100%
- 조직별로 `overdue`·재작업 루프 10% 이상, 본사 수작업 주 4시간 이상, audited exceedance miss 1건
  이상 중 최소 하나의 실제 고통이 기록됨

shadow capture가 95% 미만이거나 핵심 이벤트가 하나라도 빠지면 Gate 1을 통과하지 않고 전사 모델을
재설계한다. 실제 위험일 부족으로 KMA 품질이 미검증이어도 구매 행동은 기록할 수 있고 수기 유료 섀도는
제안할 수 있지만, 앱의 자동 후보 생성·요청·에스컬레이션은 구현하지 않는다.

### Operating Gate — 실시간 자동화를 만들 조건

최소 3개의 실제 적격 위험일과 전체 30개의 `closed loop`에서 observable한 audited exceedance miss
0건과 source provenance 100%를 충족해야 한다. KMA 정상 발표는 실제 데이터로 검증하고, 희소한
정정·해제·인증실패는 저장된 계약 fixture 재생으로 검증해도 된다. false-priority는 분포와 원인을
구매자에게 공개하되 첫 파일럿의 합격선으로 쓰지 않는다. 과거 자료 재생과 조치가 필요 없는 평상일은 이
게이트를 대신하지 않는다. 통과 전 Stage 2 구현 범위는 기존 이벤트의 수기 입력·사후 예외 목록·CSV
export에 한정한다.

Operating Gate 뒤 실시간 보조 기능에서 안전 관련 실제 누락이 한 건이라도 발생하면 즉시 자동
후보·요청·에스컬레이션을 끄고 `fallback`으로 복귀한다. 그 밖의 completion 비율은 동일 사례군에서
지표별 분모 30건 이상, 사전에 합의한 허용오차 5%p로 비교한다. 표본이 작으면 방향성만 보고 중단
판정에 쓰지 않는다. 처리시간 30% 감소는 목표지만 안전 completion보다 우선하지 않는다.

### Stage 2 — 유료 단일 폐쇄루프 앱

Gate 1 통과 후 별도 서비스 저장소에 구현한다. odeduck 저장소에는 고객별 안전 운영 로직을 넣지 않고,
재사용 가능한 공공데이터 계약·호출 개선만 upstream한다.

각 고객에 독립된 Go 웹 서비스·SQLite·암호화 백업을 배포한다. 파일럿 중에는 공유 멀티테넌트 DB로
이전하지 않는다. 최소 상태는 `Site`, `WorkBlock`, append-only `Event`, `SourceSnapshot` 네 종류로
표현하고, CSV 증빙 한 형식만 제공한다. 실제 현장 입력 링크는 Operating Gate 통과 후에만 추가한다.

Operating Gate 전에는 컨시어지 운영자가 고객 기존 채널의 이벤트를 30분 안에 수기 입력하고 본사
담당자가 매일 원본과 대조해 승인한다. Gate 뒤에는 현장관리자가 측정·수신·완료 이벤트를 직접 제출할 수
있지만, 컨시어지 정정은 사유를 남기고 본사 담당자가 승인해야 효력이 생긴다.

```text
KMA APIs → odeduck provenance adapter → 고객별 단일 컨테이너
                                          ├─ HQ 예외 목록
                                          ├─ 고객 판단·수신·완료 기록
                                          └─ append-only event CSV
```

서비스가 보존해야 할 필드는 다음과 같다.

- odeduck 데이터 PK, operation, 요청 인자, 원천 발표시각, 수집시각, raw payload hash
- 현장 좌표, 작업블록, 측정값·단위, 입력 역할과 시각
- 고객의 판단·조치 문구 버전, 승인자 역할, 지시·수신·완료·에스컬레이션 시각
- 정정·취소·fallback 이벤트와 CSV export 버전

Operating Gate 뒤 현장 링크를 추가할 때는 조직·현장·작업블록에 묶인 예측 불가능한 1회용 토큰을
발급하고 서버에는 hash만 저장하며 만료·사용·취소 뒤 재사용을 금지한다. PDF, 사진·위치 증빙,
PostgreSQL, 공유 멀티테넌시, 센서 직접 연동은 구매자 요구와 유료 갱신 전에는 추가하지 않는다.

production 배포 전에는 다음 운영·보안 체크리스트를 고객 보안담당자와 통과한다.

- 본사 사용자는 개인별 계정과 MFA를 쓰고 `hq_admin`, `hq_reader`, `concierge` 최소권한 역할을 분리
- TLS, 고객별 저장 암호화, 고객별 cloud KMS·secret manager 키와 정기 rotation
- 로그인·조회·입력·정정·export·권한변경의 append-only 접근 로그와 고객 조회 경로
- 매일 암호화 백업, production 전 복구 시험, 이후 월 1회 복구 시험과 결과 기록
- 계약된 보존기간 종료 시 원본·export·backup 삭제, 삭제 증명 제공
- 보안사고 대응 담당자, 링크·계정 즉시 폐기 절차, 계약된 통보기한(기본 24시간)과 재개 승인
- 의존성·컨테이너 취약점 검사와 critical 취약점이 남은 build의 배포 차단

### Adapter Policy

현재 확인한 KMA REST 계약이 검색·계약 검사 기능을 제공하므로 선제적인 범용 어댑터 개편은 하지 않는다.
활용신청과 표본 호출에서 다음 중 하나가 재현될 때만 odeduck 어댑터를 보강한다.

- 발표시각·유효시각·특보 해제 상태를 provenance로 보존할 수 없음
- KMA 격자 변환, pagination, 빈 응답, retry·timeout을 기존 호출 경로로 안정적으로 처리할 수 없음
- 같은 입력의 호출을 재현하거나 raw payload hash를 검증할 수 없음
- 계약 변경을 탐지하는 fixture를 만들 수 없음

완료 조건은 단기예보·기상특보 operation의 계약 fixture, 정상·빈 응답·정정·해제·인증실패 테스트,
source timestamp와 raw hash 보존이다. 조직·조치·센서·승인 로직은 odeduck에 넣지 않는다.

### Gate 2 — 상업성, Gate 1 통과 후 60일

서로 독립적인 두 조직에서 입금 또는 취소 불가 발주서를 확보해야 한다. 통과하지 못하면 제품 개발을
중단하고 구매자·문제·가격 중 반증된 가설을 기록한다.

30만~100만원은 시장가격이 아니라 초기 지불의사 가설이다. 견적 전 실제 전사·예외처리 분당 원가,
하루 270분 지원 상한, 전문가 검수, 인프라와 보안 비용을 합산한다. 직접원가보다 낮은 가격은 할인 이유와
종료일이 있는 유료 discovery 보조금으로만 허용하며 반복 가능한 가격으로 간주하지 않는다.

### Gate 3 — 확장

최소 한 조직이 유료 갱신하거나 두 번째 실제 위험기간에도 유료로 사용해야 한파·호우 또는
안전보건대행기관 채널을 검토한다. Gate 2 직후 곧바로 위험 종류나 채널을 늘리지 않는다.

## Open Questions

- 실제 예산권자는 본사 안전보건 책임자, 현장소장, 구매팀, 대표 중 누구인가?
- 최근 폭염일에 본사 한 명이 취합·추적에 쓴 시간과 누락률은 얼마인가?
- 기존 센서의 교정·측정 기록을 고객 법무·노무팀이 어떻게 인정하는가?
- 고객 보안정책이 현장 입력 링크와 외부 호스팅을 허용하는가?
- 시험가격 30만~100만원에서 조달을 시작하게 하는 결과물은 무엇인가?
- 폭염 종료 뒤 같은 운영가치를 반복 구매하는가?

이 질문들은 구현으로 답하지 않는다. 인터뷰 기록, 실제 업무자료, 섀도 행동, 결제로 답한다.

## Reviewer Concerns

세 차례 독립 검토 뒤 다음 항목은 문서만으로 해소할 수 없어 실행 전 증거가 필요하다.

   `audited exceedance miss`를 계산할 수 없다. 이 경우 자동 위험 우선순위는 금지한다.
2. **가격과 수작업 원가:** 30만~100만원은 지불의사 가설일 뿐이다. 실제 루프당 시간과 전문가·보안
   비용을 확인하기 전 지속 가능한 가격을 주장하지 않는다.
3. **자체 호스팅 보안 승인:** 위 체크리스트는 최소선이다. 고객 보안정책과 침해 대응·보존 요구를
   production 배포 전에 서면 승인받아야 한다.
